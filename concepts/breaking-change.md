# Breaking change & semver

## 판정 기준은 "영향의 크기"가 아니다

정의는 딱 하나:

> **"내 코드를 고쳤을 때, 그걸 쓰던 남의 코드가 손대지 않으면 더 이상 안 돌아가는가?"**

규모와 무관하다.

- 규모 크지만 breaking ✗ — 내부 전면 리팩터링, 성능 3배 개선 (공개 API 그대로면 아님)
- 규모 작지만 breaking ✓ — 프로퍼티명 한 글자 수정 (`leadingImage` → `startImage`)

## 종류

제거 / 이름 변경 / 시그니처 변경(필수 파라미터 추가) / **동작·기본값 변경**

마지막이 제일 고약하다. 앞 셋은 컴파일러가 시끄럽게 잡아주는데 **조용한 breaking**은 화면만 달라진다.

## semver

| | 뜻 |
|---|---|
| PATCH | 버그 수정 |
| MINOR | 호환되는 기능 추가 |
| **MAJOR** | **호환 깨짐** |

3.x → 4.0인 건 작업량이 많아서가 아니라 **깨는 게 들어있어서**다.

## 경계선 = `public`이 붙은 것들

공개 인터페이스가 명시적이면 **무엇이 breaking인지 판단할 근거가 코드 안에 있다.** 그래서 자동 검사(preflight)의 첫 항목이 대개 "공개 API가 바뀌었는지"다.
