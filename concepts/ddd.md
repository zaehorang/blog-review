# DDD (Domain-Driven Design) / DDD-lite

소프트웨어 구조를 **비즈니스 도메인의 개념과 언어**에 맞춰 설계하는 접근. Eric Evans의 2003년 책에서 나왔다. 코드를 기술 단위(handler, repository)가 아니라 비즈니스 개념 단위(신용점수, 대출)로 나눈다.

## 전략적 설계 (경계 나누기)

- **유비쿼터스 언어** — 개발자와 도메인 전문가가 같은 용어를 쓰고 코드에도 그 용어를 그대로 쓴다.
- **바운디드 컨텍스트** — 그 용어가 일관된 의미를 갖는 경계. 같은 "고객"이 컨텍스트마다 다른 뜻이어도 된다. 경계를 긋는 일이 곧 "이 단어는 여기서 이 뜻"을 정하는 일이다. (언어를 "조직 전체 공용"으로 오해하기 쉽다.)
- **도메인 분류** — core(경쟁력의 핵심) / supporting(보조) / generic(범용).

## 전술 패턴 (무겁다)

Aggregate, Entity, Value Object, 이벤트 소싱 등. 강력하지만 도입 비용이 크다.

## DDD-lite

공식 용어라기보다 관용 표현. 전술 패턴의 무거운 부분은 빼고 **경계 나누기 + 레이어링**만 가져온다. 뱅크샐러드 글의 채택/보류가 전형적인 예다.

- 채택: 바운디드 컨텍스트(폴더 하나 = 개념 하나), 컨텍스트별 4계층(handler / application / domain / infrastructure), 단방향 의존성.
- 보류: Aggregate, 이벤트 소싱.
- **단방향 의존성(포트/어댑터):** domain이 필요한 기능을 인터페이스(포트)로 선언하고, 실제 구현(어댑터)은 infrastructure에 둔다. domain은 저장소가 MySQL인지, 평가사가 KCB인지 몰라도 된다.

지키지 못하는 정교한 규칙보다 지키는 단순한 규칙이 낫다는 판단이다. Clean Architecture(Robert C. Martin)와 겹치는 부분이 크다.

## 흔한 실패

기준이 사람 머릿속에만 있으면 PR마다 흔들려서, 개념이 아니라 **데이터 출처(벤더) 이름으로 폴더가 묶이는** 식으로 무너진다.
