# 이벤트 기반 동시성 (왜 메모리가 줄까)

"연결마다 스레드/프로세스를 하나씩" vs "워커 하나가 여러 연결을 이벤트로 돌본다".

```
스레드/프로세스 모델   연결 1개 = 스레드 1개 (기다리는 동안에도 점유)
이벤트 기반 모델      워커 1개가 연결 수천 개 — 커널에 "준비되면 알려줘"(epoll 등)
                     준비된 연결만 꺼내 처리
```

여기서 **이벤트 = 소켓 상태 변화**("읽을 데이터가 왔다", "쓸 수 있게 됐다").

## "이벤트가 많으면 똑같지 않나?"의 답

- **줄어드는 건 일의 양(CPU)이 아니라 "기다리는 연결의 비용"이다.** 구분할 게 둘이다 — *처리 중인 일* vs *연결을 붙잡고 있는 것 자체*.
- 연결 대부분은 **기다리는 중**이다(느린 클라이언트의 전송, 업스트림 응답 대기). 스레드 모델에서는 대기 중에도 스택 메모리·전환 비용을 낸다. 이벤트 모델에서는 연결이 작은 상태 구조체일 뿐이라 대기는 거의 공짜.
- **이득은 "연결은 많은데 대부분 대기 중인" 워크로드(I/O 바운드, 장기 연결)에서 크고, CPU를 계속 쓰는 일이면 작다.** 글은 이 조건을 적지 않는다.
- 연결 수가 늘어도 워커 수는 일정하다(보통 코어 수 기준).

## 분산과는 독립이다

이벤트 기반은 **한 프로세스가 연결을 다루는 방식**(동시성 모델)이고, 분산은 **요청을 어느 서버로 보낼지**(라우팅)다. 이벤트 기반이 아니어도 분산은 되고, 서버가 1대여도 이벤트 기반이다 — "이벤트 기반으로 분산해준다"는 둘을 묶은 오해.
