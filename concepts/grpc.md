# gRPC

Google이 만든 [RPC](rpc.md) 패러다임의 구체적 구현체. [HTTP/2](http.md)를 전송 프로토콜로, [Protocol Buffers](protocol-buffers.md)를 기본 직렬화 포맷으로 쓴다(JSON도 지원은 하지만 기본값은 아님).

## 특징

- **서비스 지향** — 클라이언트가 서버의 함수를 직접 호출.
- **다양한 스트리밍** — 단방향, 서버 스트리밍(1:N), 클라이언트 스트리밍(N:1), 양방향 스트리밍(N:N). HTTP/2가 하나의 연결 위에 여러 독립 스트림을 정의해주기 때문에 가능 → [TCP는 원래 양방향](tcp-vs-udp.md)인데, 그 능력을 애플리케이션 레벨 메시지 스트림으로 구조화해서 노출한 것.
- **고성능** — 바이너리 직렬화 + HTTP/2 멀티플렉싱으로 대용량·저지연 처리에 유리.
- **자동 코드 생성** — proto 정의로 클라이언트/서버 스텁을 자동 생성해 개발 시간 단축.

## 트레이드오프 — 긴밀한 결합

클라이언트·서버가 같은 proto 정의를 공유해야 해서 REST보다 결합이 긴밀하다. 여기서 "확장성"을 물을 땐 두 축을 나눠야 한다:

| 축 | gRPC | REST |
|---|---|---|
| 성능 확장성 (scalability) | 유리 — 바이너리 + 멀티플렉싱 | 상대적으로 불리 |
| API 진화 용이성 (evolvability) | 불리 — 스키마 변경 시 양쪽 재생성·조율 필요 | 유리 — JSON 필드 추가/생략에 관대 |

다만 proto는 필드 번호 기반이라 **새 필드 추가는 구버전 클라이언트를 안 깨뜨리도록 설계**돼 있다(하위 호환 스키마 진화). "매번 다시 컴파일 안 하면 무조건 깨진다"가 아니라 "조율 비용이 REST보다 크다" 정도로 보는 게 정확하다.

**결합도-변경빈도 짝:** 결합이 긴밀하고 코드 생성으로 굳어진 만큼, **API가 잘 안 변하는 안정적인 내부 마이크로서비스**에 적합하다. 반대로 REST는 결합이 느슨해서 **변경이 잦은 서비스**에 적합.

## 브라우저에서 직접 못 쓰는 이유

브라우저 API(fetch/XHR)가 gRPC에 필요한 저수준 HTTP/2 프레임 제어(trailer 등)를 노출하지 않는다. 그래서 `gRPC-Web`이라는 별도 프록시 계층이 필요하다.
