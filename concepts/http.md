# HTTP

[TCP](tcp-vs-udp.md) 위에서 도는 **응용 계층 프로토콜**. REST도 RPC(gRPC)도 결국 HTTP 위에서 돈다.

## 왜 필요했나

TCP는 그냥 바이트 스트림만 옮긴다. "연결을 매번 새로 맺어야 해서" 문제가 아니라 (연결은 handshake 한 번으로 이미 해결됨) — **"이 바이트들이 무슨 의미인지"에 대한 공통 약속이 없다**는 게 진짜 문제였다.

HTTP는 요청 줄 / 헤더 / 바디로 메시지 형태를 고정해서, 클라이언트·서버가 매번 "요청이 어디서 끝나고 바디가 어디서 시작하는지" 새로 정의할 필요를 없앴다. 즉 HTTP가 해결한 건 "연결 반복"이 아니라 **"메시지 형식·의미의 표준화"**다.

## 버전

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 특징 | 커넥션당 요청 하나씩 순차 처리 (헤드오브라인 블로킹) | 하나의 연결에서 여러 요청/응답을 동시에 흘림 (**멀티플렉싱**) | UDP 기반 QUIC 사용 |
| 지원 | 거의 모든 곳 | 주요 브라우저 전부 기본 지원 | 점진 확산 중 |

**흔한 오해:** "REST는 HTTP/1.1, gRPC는 HTTP/2"로 딱 나뉜다는 생각. 오늘날 브라우저는 HTTP/2를 기본 지원하고, REST API도 HTTP/2 위에서 흔히 돈다. 진짜 차이는 [gRPC](grpc.md)가 HTTP/2의 멀티플렉싱·trailer 헤더 같은 기능을 **필수로 요구**해서 2가 아니면 동작 자체가 안 된다는 것 — REST는 그 기능이 굳이 필요 없어서 1.1로도 충분할 뿐이다.

브라우저가 HTTP/2를 지원해도 gRPC를 브라우저에서 직접 못 쓰는 이유는, 브라우저 API(fetch/XHR)가 gRPC에 필요한 저수준 HTTP/2 프레임 제어를 노출하지 않기 때문. 그래서 `gRPC-Web`이라는 별도 프록시 계층이 존재한다.
