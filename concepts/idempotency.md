# 멱등성 (Idempotency)

**같은 요청/이벤트를 몇 번을 반복해서 처리해도 결과가 한 번 처리한 것과 똑같아야 한다**는 성질.

비유: 엘리베이터 버튼. 한 번 누르든 초조해서 다섯 번 연타하든 그 층엔 한 번만 온다. 반대로 "계좌에 만원 입금" 같은 요청을 실수로 세 번 보내면 삼만원이 들어가버리는 게 멱등하지 않은 경우다.

[최종 일관성](eventual-consistency.md)을 택해 비동기 이벤트로 서비스를 연동하면, 메시지 브로커는 보통 "적어도 한 번(at-least-once)"은 전달해도 "정확히 한 번(exactly-once)"이나 순서는 보장하지 않는 경우가 많다. 그래서 비동기 전환은 멱등성 확보를 세트로 요구한다.

## 현업에서 확보하는 방법

| 방법 | 판단 기준 | 비고 |
|---|---|---|
| **상태 기반 가드** | 엔티티의 현재 상태를 보고 "이미 그 상태면 스킵" | 가장 단순. 상태 머신이 단순(한 방향 전이)할 때 충분 |
| **멱등성 키 (Idempotency Key)** | 요청마다 고유 ID를 붙이고 "처리한 적 있나" 별도 이력 테이블에 기록 | 결제 API가 대표적 (예: `Idempotency-Key` 헤더). 상태와 무관하게 어떤 액션이든 감쌀 수 있어 더 범용적 |
| **DB Unique Constraint** | 요청/이벤트 ID에 유니크 인덱스를 걸어 중복 INSERT를 DB가 거부 | 애플리케이션 버그가 있어도 막아주는 최후 방어선 |
| **Upsert** | "있으면 갱신, 없으면 삽입"으로 반복 실행 자체를 안전하게 설계 | 연산 자체를 멱등하게 만드는 방식 |
| **멱등성 소비자 패턴** | 메시지 브로커 컨슈머가 처리한 메시지 ID/오프셋을 저장해두고 중복 무시 | Kafka/RabbitMQ 컨슈머에서 흔함 |

가르는 축은 두 개다 — **어디서 막나**(애플리케이션 로직 / DB 제약 / 인프라)와 **무엇으로 식별하나**(도메인 상태 자체 / 별도의 명시적 ID).

### 예시 흐름 — 상태 기반 가드
```
[상태: InApproval]
이벤트①(Approved) 도착 → InApproval이니 처리 → Approved로 전이
같은 이벤트②(재전송) 도착 → 이미 Approved → 조기 리턴, 아무 것도 안 함
```

### 예시 흐름 — 멱등성 키
```
[처리 이력 테이블: 요청ID]
요청①(id=abc123) 도착 → 이력에 없음 → 실행 + 이력 기록
같은 요청②(id=abc123) 재전송 → 이력에 있음 → 실행 안 하고 저장된 결과만 반환
```
