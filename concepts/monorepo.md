# 모노레포

여러 패키지를 한 저장소에서 관리하는 방식.

## 모노레포는 배포를 없애지 않는다

흔한 오해가 "따로 배포·트래킹 없이 한 번에 수정하고 배포한다"인데 아니다.

> **모노레포가 배포를 없앤 게 아니라, 개발하는 동안의 루프에서 배포를 걷어낸 것.**

모노레포 밖 프로젝트를 위한 레지스트리 배포 경로는 그대로 유지된다.

## 진짜 이득 = 피드백 루프 단축

"피드백 루프"는 릴리즈 과정이 아니라 **개발 중에 방금 고친 게 눈으로 확인되기까지**의 시간. 하루 수십~수백 번 도는 사이클이다.

```
[전] 버튼 수정 → commit → 버전업 → publish → 서비스에서 install → 확인   ≈ 수 분
[후] 버튼 수정 → 저장 → 화면에 반영 (HMR)                              ≈ 수 초
```

iOS 비유: **원격 SPM 패키지 참조 vs 로컬 패키지 참조.** 전자는 프레임워크 한 줄 고칠 때마다 commit·tag·resolve, 후자는 그냥 빌드. **앱스토어 배포는 어느 쪽이든 똑같이 한다.**

→ 이득은 라이브러리가 하루에도 몇 번씩 바뀌는 **초기 구성 시점에 가장 크고, 안정화되면 줄어든다.**

## `workspace:*`

`package.json`에 버전 대신 **"옆 폴더"**를 쓰는 것.

```json
// apps/flight/package.json
"dependencies": { "@company/core": "workspace:*" }   // 레지스트리 말고 packages/core를 심볼릭 링크
```

보통은 `"^1.2.3"`처럼 버전을 쓰고 패키지 매니저가 레지스트리에서 받아온다. `workspace:*`는 **"레지스트리 가지 말고 이 저장소 안의 `packages/core`를 써"**(`*`는 버전 아무거나). 배포할 땐 `pnpm publish`가 이걸 실제 버전으로 자동 치환해줘서 모노레포 밖 프로젝트도 정상 설치된다.
