# REST (Representational State Transfer)

**프로토콜이 아니라 설계 스타일.** "리소스를 URI로 표현하고, HTTP 메서드(동사)로 조작하자"는 일련의 제약 조건. [HTTP](http.md) 위에서 구현되지만 그 자체가 프로토콜은 아니다.

- **URI = 명사(리소스)**, **HTTP 메서드(GET/POST/PUT/DELETE) = 동사(동작)**. 예: `POST /orders`
- 엔터티(리소스) 지향 설계 — 클라이언트는 서버가 가진 "것"을 조작한다는 관점.
- **RESTful**은 "어떤 API가 REST 제약을 따른다"는 형용사. 별개 기술이 아니라 REST 원칙을 따랐다는 수식어일 뿐.

## 느슨한 결합이 핵심

클라이언트는 URI와 메서드만 알면 되고, 서버 내부 구현(함수명, 클래스 구조)을 몰라도 된다. 그래서:
- 클라이언트·서버가 **서로의 구현을 몰라도** 동작 → 느슨한 결합
- 데이터 형식은 보통 JSON — 필드가 추가/생략돼도 클라이언트가 대충 파싱 가능
- **변경이 잦은 소프트웨어**에 적합 (서버가 바뀌어도 클라이언트 재빌드가 강제되지 않음)

## RPC와의 대비

REST가 "리소스를 조작"한다면 [RPC](rpc.md)는 "함수를 호출"한다 — 관점 자체가 다르다.
