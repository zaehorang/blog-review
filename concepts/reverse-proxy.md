# 리버스 프록시 / 게이트웨이

**프록시 = 대리인.** 갈리는 건 "누구의 대리인이냐"다.

| | 포워드 프록시 | 리버스 프록시 |
|---|---|---|
| 대리하는 쪽 | **클라이언트** (예: 회사 PC → 인터넷) | **서버** (인터넷 → 내부 서버들) |
| 클라이언트가 아나? | 안다 (프록시를 설정함) | **모른다** (그냥 서버인 줄 앎) |
| 서버가 아나? | 진짜 클라이언트를 모름 | 진짜 서버가 누군지 클라이언트가 모름 |

대리하는 방향이 반대라서 "리버스". 요청이 향하는 뒤쪽 서버를 **upstream**이라 부른다 (뒤로 보내는 건 이벤트가 아니라 **요청**).

## 정의는 "분산"이 아니다

리버스 프록시의 정의는 **서버 앞에서 요청을 대신 받아 뒤로 전달**하는 것. 서버가 1대여도 리버스 프록시다. 분산(로드밸런싱)은 그 위에 얹는 기능 하나일 뿐이다 — "결국 트래픽 분산 정도?"는 절반만 본 것.

하는 일들:
- **L7 라우팅** — `/` → web, `/auth` → keycloak, `/api` → be. 클라이언트는 **주소 하나**만 안다. (게이트웨이로 느껴지는 부분)
- **분산** — `upstream`으로 여러 서버에
- **[TLS 종료](tls-termination.md)** — HTTPS를 한 곳에서
- **정적 파일 직접 응답**, 압축, 캐시
- **느린 클라이언트 대신 받아주기** — 앱 서버 워커가 느린 전송을 기다리며 묶이지 않게 ([이벤트 기반](event-driven-concurrency.md))

## 꼭 필요한가 — 아니다, 조건이 있다

필요해지는 쪽: 서비스가 **둘 이상의 별개 배포 단위**로 쪼개져 한 주소로 묶고 싶을 때(가장 큰 이유) · 서버를 여러 대로 늘릴 때 · TLS를 한 곳에서 처리할 때 · 앱을 직접 노출하기 싫을 때.
없어도 되는 쪽: 서비스 1개·서버 1대(FastAPI+Jinja2, 정적 HTML/CSS/JS 하나) · 플랫폼이 이미 그 역할을 해주는 경우(ALB, Vercel, Cloud Run, k8s [Ingress](kubernetes-ingress.md)).

- **필수인 건 Nginx가 아니라 "앞단 계층이라는 역할"이다.** 구현체는 Nginx·Caddy·Traefik·클라우드 LB 등으로 교체된다.
- **비용:** 운영 대상이 하나 늘고, 설정 실수(502/504, [리다이렉트 루프](http-redirect.md), `proxy_pass` 슬래시)가 이 계층에서 나온다.
- 라우팅이 한 출처로 묶이면 브라우저 입장에서 **같은 출처**가 돼 [CORS](cors.md)가 필요 없어진다.
