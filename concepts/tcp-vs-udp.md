# TCP vs UDP

같은 [전송 계층](network-layers.md)에서 신뢰성과 속도 중 무엇을 우선할지 가르는 두 프로토콜.

| | TCP | UDP |
|---|---|---|
| 연결 | 연결 지향 — 3-way handshake로 먼저 연결 수립, 4-way handshake로 종료 | 비연결형 — handshake 없이 그냥 전송 |
| 신뢰성 | 순서 보장 + 유실 패킷 재전송 + 흐름/혼잡 제어 | 보장 없음 — 유실·순서 뒤바뀜 그대로 |
| 속도 | 신뢰성 챙기는 만큼 오버헤드 있음 | 오버헤드 적어 빠름 |
| 비유 | 등기우편 (수신 확인, 순서 보장) | 그냥 우편 던지기 |
| 대표 사용처 | 웹(HTTP), 파일 전송, DB 연결 — 정확성이 속도보다 우선 | 실시간 영상통화, 게임, DNS — 속도가 약간의 손실보다 우선 |

## TCP는 원래 양방향(full-duplex)이다

하나의 TCP 연결로 양쪽이 **동시에** 데이터를 주고받을 수 있다. 이건 TCP가 태생부터 가진 능력이지 상위 프로토콜이 새로 만든 게 아니다.

그래서 "REST는 단방향, gRPC는 양방향"이라는 차이는 **TCP의 능력 차이가 아니라 그 위의 애플리케이션 계층(HTTP·REST·gRPC)이 그 능력을 쓰기로 약속했는지의 차이**다. REST는 요청-응답을 1:1로 못박아 둔 설계 선택이고, gRPC([HTTP/2](http.md) 기반)는 하나의 연결 위에 여러 독립 스트림을 정의해서 그 능력을 명시적으로 노출한다.

> "가능한가"는 전송 계층이 이미 답을 줬고, "그 가능성을 어떻게 쓰기로 했나"는 그 위층의 설계다 — 하부의 잠재력과 상위의 의미론적 계약을 구분해서 봐야 한다.

## 참고 — HTTP/3와 QUIC

최신 HTTP/3는 TCP가 아니라 **UDP 기반의 QUIC**을 쓴다. TCP의 신뢰성 로직(순서 보장, 재전송)을 애플리케이션 레벨에서 UDP 위에 다시 구현해, TCP의 단점(연결 수립 지연, 헤드오브라인 블로킹)을 없애면서 신뢰성은 유지한 설계.
