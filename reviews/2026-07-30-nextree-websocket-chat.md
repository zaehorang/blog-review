# Nextree — WebSocket 채팅 서비스 설계

## 🔑 한 줄 요약
> 소켓으론 "내용물" 대신 **"이벤트 신호"만** 흘리고 실제 데이터는 클라가 조회 API로 다시 가져오게 하면 — 콘텐츠 검증이 한 곳으로 통일되고 오프라인 복구까지 공짜로 깔끔해진다.

## 📌 무슨 글 (중립 요약)
- 실시간 채팅의 핵심 과제: "남이 보낸 메시지를 나에게 즉시" 어떻게 알릴까.
- 답: WebSocket + STOMP로 서버가 **push**. 단, 본문이 아니라 **이벤트 신호만** 보내고 클라가 재조회.
- 겪은 문제: 방 삭제/나가기 시 알림 **대상을 못 찾음** → 대상 확보 → 삭제 → 알림 순으로 쪼개 해결.

---

## 🧠 내가 이해한 것 → 교정 (오늘의 핵심)

**① 웹소켓을 왜 쓰나**
- 내 생각: HTTP는 매번 인증/연결하니, 한 번 인증하고 통로 열어 비용 절감.
- 교정: (a) 웹소켓은 TCP "대신"이 아니라 **TCP "위에서"** 돈다 — HTTP 연결을 업그레이드. 그래서 "HTTP 요청/응답 vs 웹소켓 지속연결" 구도. (b) 🔑 진짜 1순위 이유는 인증 절감이 아니라 **server push** — HTTP는 서버가 먼저 못 말 걸어서 polling 해야 함. "남이 보낸 메시지 즉시 도착"이 딱 이걸 요구. 인증 절감은 부차적.

**② 인증 방식**
- 내 생각: 서로 토큰으로 계속 빠르게 확인하며 통신.
- 교정: **연결할 때 1회만** 검증(handshake에 토큰 실어서). 이후엔 **"열린 연결 자체가 신분증"** — 메시지마다 재인증 안 함. 그게 "빠르다"의 정체.

**③ "온라인에게만" 인데 카톡은 꺼도 알림 오잖아? (제일 헷갈렸던 것)**
- 해소: **서로 다른 두 개의 알림**을 하나로 봤던 것.
  - **이벤트 알림** = 웹소켓, 앱 켜진 **온라인**일 때만. 화면 실시간 갱신용. ← 이 글의 범위.
  - **푸시 알림** = APNs(iOS)/FCM(안드), **OS가 관리**, 앱 꺼도 옴. 재유입용.
  - 실서비스는 **둘 다** 씀. 이 글은 웹소켓 레이어만 다룬 것.

**④ "여기서 말하는 알림 = 이벤트 알림?"** → 맞음. (스스로 도달)

---

## ❓ 궁금증 → 해소

- **"권한 검증 통일" = 알림은 값을 안 나른다는 뜻?** → 맞음. 알림은 **초인종**, 값은 조회 API로만 나옴.
- **ⓐ 연결 인증 vs ⓑ 콘텐츠 권한** — 통일되는 건 ⓑ.
  - ⓐ "너 로그인 유저 맞아?" → 연결 시 1회, **A·B 둘 다 동일**.
  - ⓑ "너 이 메시지 볼 권한 있어?" → **데이터마다**. 소켓이 내용물을 나르면(설계A) 여기 검증이 붙어서 조회 경로와 **중복**됨.
- **"오프라인이 이벤트를 놓친다"** = 설계A(내용물 배달)의 문제. 신호만 보내는 설계B는 **재접속 후 조회 한 번 = 최신 복구**, 이벤트 재생 불필요.
- **검증은 누가?** → **항상 서버.** 진짜 검증(ⓑ)은 클라가 시작하는 **조회 요청**에서만. 알림 푸시는 서버가 먼저 보내지만 내용이 없어 검증할 게 없고 "대상만" 고름.

---

## ⚖️ 두 설계 비교

| | 설계 A (내용물 배달) | 설계 B (신호 + 재조회) ← 이 글 |
|---|---|---|
| 소켓이 나르는 것 | 실제 본문/사진 | "뭔가 생겼다" 신호만 |
| 콘텐츠 검증(ⓑ) 위치 | 소켓 푸시 + 조회 = **두 곳** | 조회 **한 곳** |
| 소켓 트래픽 | 무거움 | 가벼움 |
| 오프라인 복구 | 서버가 밀린 것 **재생** 필요 | **조회 한 번**이면 끝 |
| 복잡도 | 높음(중복 로직 + 재생 큐) | 낮음(단일 경로) |

## 🐛 겪은 문제 & 해결 (방 삭제/나가기)
- 문제: 알림 대상을 찾을 정보가 **삭제 후엔 사라져** 대상을 못 찾음.
- 해결: **변경 전에 대상 스냅샷 확보 → 삭제 → 알림.** 이벤트 성격을 둘로 분기.
- 내 질문(스키마 의존): soft delete면 데이터 남으니 안 날아가지 않나?
  → **반만 맞음.** 행은 남아도 조회 필터(`WHERE left_at IS NULL` 등)에 걸려 **대상에서 누락** 가능. 그래서 hard/soft 무관하게 **"변경 전 스냅샷"이 안전.**

---

## 🔁 도메인 안 가리는 패턴 (전이 가능)
1. **실시간 = "신호 + 재조회".** 소켓은 진실의 원천이 아니라 "새로고침해" 방아쇠. 놓쳐도 재조회로 복구되니 오프라인·재접속이 공짜로 깔끔.
2. **데이터 경로를 하나로 못 박으면** 권한/검증 로직이 한 곳 → 중복 버그 제거.
3. **read-then-write:** 쓰기가 파괴할 정보는 쓰기 전에 스냅샷으로 확보. (탈퇴 후 정리, 주문 취소 후 정산 등 어디든)
4. **두 겹 알림:** 온라인(웹소켓) + 오프라인(푸시)은 다른 레이어. 실시간 기능 설계 시 둘 다 떠올리기.

## 🎯 오늘 챙길 한 줄
> 실시간 기능을 볼 땐 먼저 물어라 — **"소켓이 진실을 나르나, 신호만 나르나?"** 신호만 나르게 하면 검증·오프라인·확장이 전부 쉬워진다.
