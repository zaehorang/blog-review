# DelightRoom — Claude Code를 42주 쓴 iOS 팀의 워크플로우

## 🔑 한 줄 요약
> `CLAUDE.md`는 내용을 담는 곳이 아니라 **"내용으로 가는 길을 그리는 라우터"** — 트리거(언제)→순서(어디로)만 두고 살은 `.claude/` 하위로 위임한다. 그리고 스캐폴딩엔 두 종류가 있다: **우리만 아는 사실(영구)** vs **모델이 못해서 만든 임시책(유통기한 있음)**.

## 📌 무슨 글 (중립 요약)
- 글로벌 1위 알람앱 알라미 iOS 팀(SwiftUI/TCA, SPM 모듈화)이 Claude Code를 **메인 에이전트**로 42주 쓴 워크플로우 공유.
- 중심 주장: 반복 작업을 워크플로우로 자동화하되 **Agent/Skill/MCP는 최소한만 팀 공유.** 많이 쓰는 게 아니라 **적절한 걸 잘 고르게** 하는 게 핵심.
- 구성: `CLAUDE.md`(키워드 트리거→문서 라우팅) · `.claude/workflows` · 스킬(`/learn`, `agent-device`) · MCP(Xcode/Figma/Linear) · self-hosted GitHub Actions CI/CD.
- 이득: 작은 작업은 원샷으로 배포+QA까지. "스프린트에서 개발이 병목이 아니다."
- 저자 견해/한계: **복잡한 자동화를 직접 만들기보다 모델 발전을 기다리는 게 현명**했다. 대신 많아진 터미널 탭에 "두뇌 토큰"을 더 쓰게 됨.

## 🧠 내가 이해한 것 → 교정 (오늘의 핵심)

**① CLAUDE.md = Navigation**
- 내 생각: 규칙/툴이 많아 다 못 담으니, 각 문서의 route만 설명해 에이전트가 적재적소에 읽게 함. 컨텍스트를 작게 유지하려는 것.
- ✅ 정확. 💡 이건 **lazy loading** — 모든 규칙을 항상 밀어넣으면 토큰 낭비 + 관련 없는 규칙이 판단을 흐림(신호↓). "키워드 감지 → 그때 그 문서만." 스킬/MCP를 최소만 공유하는 것도 같은 원리 — **선택지가 적어야 잘 고른다.**

**② 살아남는 스캐폴딩 (이 글의 진짜 교훈)**
- 저자는 "복잡한 시스템 만들지 말고 모델을 기다려라"면서 정작 CLAUDE.md·워크플로우를 열심히 만듦 → 모순처럼 보임.
- 🔧 화해: 경계는 **"에이전트가 스스로 알 수 있는 것 vs 우리만 아는 것".**
  - 버릴 것: *복잡한 결정론적 로직*("이 경우엔 이렇게" 하드코딩). 모델 좋아지면 낡음. (= "codex 나오니 문서 명시가 필요 없어졌다"의 정체.)
  - 남길 것: *컨텍스트 정리*(구조·팀 규칙·어디에 뭐가 있나). 모델이 못 맞히는 정보라 안 사라짐.
  - 알라미가 만든 건 대부분 뒤쪽이라 살아남는 것.

**③ figma-to-swiftui 스킬**
- 내 생각: 따로 만든 게 인상적, 시도해볼 만.
- 💡 진짜 포인트는 "변환" 자체가 아니라 **하드코딩 색/폰트/간격을 금지하고 디자인 토큰만 쓰게 강제**한다는 것. 스킬 = 변환기가 아니라 **"팀 규칙을 코드에 각인시키는 가드레일".** 만들 때 "무엇을 하게 하나"보다 "무엇을 못 하게 하나"가 값지다.

**④ Taste의 경계 (스킬 공유 기준)**
- 내 생각: 개발에도 taste가 있다. 공통으로 지켜야 할 것만 공유, 나머진 개인 관리.
- ✅ + 💡 taste를 둘로 쪼개면 선명해짐: **취향으로서의 taste**(개인 선호)→개인 관리 / **제약으로서의 taste**(어기면 팀에 해)→공유하되 **강제(가드레일)로** 박음. 경계는 "공통이냐"가 아니라 **"어겼을 때 해가 되냐".**

## ❓ 궁금증 → 해소

**Q. "증분빌드로 빠른 피드백 루프"가 무슨 뜻?**
- 증분 빌드 = 바뀐 파일+의존분만 재컴파일. 대형 모듈 프로젝트는 클린 몇 분 vs 증분 몇 초.
- Xcode MCP는 새 빌드를 맨바닥에서 띄우는 게 아니라 **열려 있는 Xcode를 그대로 조작** → 캐시(DerivedData) 재활용 → 증분 혜택.
- 피드백 루프 = [수정→빌드→확인→수정] 한 바퀴. 이게 몇 초냐 몇 분이냐가 에이전틱 생산성을 좌우. **빠르면 에이전트가 더 자주 시도·자가교정.**

**Q. agent-device가 뭐야?**
- iOS/Android **UI 자동화 CLI.** 에이전트가 실제 실행 중인 앱을 조작하게 함.
- 화면을 스크린샷이 아니라 **접근성 트리를 압축한 스냅샷**(구조화 텍스트)으로 읽음 → 토큰 싸고 정확.
- 킬러 포인트: 일회성 매크로가 아니라 **결정론적·재현 가능** → 그냥 클릭이 아니라 **E2E 테스트 도구**로 승격 가능.
- 연결: 에이전트가 코드 짜고 → agent-device로 자기가 짠 걸 앱에서 눌러 검증 → 루프가 닫힘.

## 🔁 도메인 안 가리는 패턴 (전이 가능)
1. **설정/문서는 라우터로.** 진입점엔 "언제→어디로"만. 콘텐츠는 (맥락 references / 절차 workflows / 검증 checklists)로 종류별 분리. → 잎만 고치고 진입점은 안 건드림 + 컨텍스트 작게.
2. **스캐폴딩엔 두 종류.** *우리만 아는 사실(영구)* vs *모델이 못해서 만든 임시책(유통기한)*. 임시책은 **만들 때부터 "언젠가 지운다"를 전제**로 만들고, 모델 바뀔 때마다 **빼보고** 재평가. (대부분 팀은 추가만 하고 안 뺌.)
3. **명시 > 암시.** 자연어 키워드 트리거는 흔한 경우 편의층. **애매하거나 치명적인 지점만 명시 호출**(`/deploy`)로 뺀다. 오분류를 막는 게 아니라 위험한 곳만 사람이 이름을 부른다.
4. **가드레일이 대신 보게.** 개발자 역할이 작성자→검수자로 이동하면 검수가 새 병목. checklist(REQUIRED)·테스트·E2E로 **검증을 자동화**해 사람 검수를 전수→표본으로 줄이는 게 "관리 잘한다"의 정체.
5. **강제할 규칙은 스킬/가드레일로.** 공유된 "취향"이 아니라 코드에 각인된 "제약"으로. (예: 디자인 토큰만 허용)
