# 토스 — LLM은 똑똑한데 왜 우리 회사 일은 모를까 (Topic)

## 🔑 한 줄 요약
> 사내 지식은 "검색 잘 되게" 만들어도 안 믿긴다. 답을 만드는 대신 **답의 출처·최신성·충돌을 '상태'로 관리하는 계층(Topic)**을 깔고, 비결정적 판단(모델)은 꼭 필요한 곳만 쓰고 나머지는 hash·규칙으로 못 박으면 — AI 답을 "믿을 수 있게" 된다.

## 📌 무슨 글 (중립)
- 문제: LLM이 공개 지식은 답하는데, 문서·코드·메신저에 흩어진 사내 정보는 신뢰성 있게 못 다룸. 검색 품질을 올려도 최신성·충돌·맥락 판단이 안 됨.
- 해결: 모든 출처를 공통 `ContentUnit`으로 정규화(원문 주소 `source_uri` 보존) + 신뢰도를 6축으로 관리 + 충돌은 자동 병합 안 하고 `disputed`/`stale_risk` **상태로 노출** → 사람은 진짜 문제 지점만 판단.
- 6축: Granularity(단위)·Faithfulness(근거)·Staleness(최신성)·Canonicality(정체성)·Consistency(일관성)·Coverage(완성도).

---

## 🧠 내가 이해한 것 → 교정 (핵심)

**① 전체 방향** — "LLM+사람이 함께 쓸 수 있는 신뢰 가능한 컨텍스트를 관리하자."
- ✅ 맞음. 그리고 내가 겪는 문제(에이전트 rubric/eval)랑 같은 뿌리로 읽음.

**② 문서/메시지/코드를 '의미 단위'로 쪼갠다 (Granularity)**
- ✅ 문서는 제목 계층 보존 → query 시 상위 맥락이 같이 딸려오고, 사후 수정도 단위별로 국소화.
- ✅ 메시지는 낱개가 아니라 **스레드**(질문→논의→결론)를 한 단위로.
- ✅ 코드는 규칙 기반 파싱(LLM 안 씀) + `source_uri`/spans(파일·줄·심볼·`commit_sha`)로 원문 앵커.
  - 🔧 이 앵커의 1순위 목적은 '이동'보다 **'검증 가능성'** — 나중에 그 줄이 그대로인지(hash) 대조하려고 위치를 박아둠.

**③ CodeSemanticCard**
- ✅ 코드를 대신하는 문서가 아니라 **비즈니스 로직을 한 단계 추상화한 계층**. 카드만 신뢰하지 않고 LLM이 실제 코드 span을 다시 읽어 검증.
- 보강: 카드는 "**여러 심볼을 가로지르는 동작·규칙**"을 설명(단일 함수보다 상위). 카드 자체도 규칙 기반 검증(줄 실존? 뒷받침 span 있나? 유사 카드 과도 반복 아닌가?).

**④ extract 3단계 (변경에 반응하는 파이프라인)** — 질문에서 정리됨
- ✅ 경로에 실제 내용 있나 → 저장 시점 대비 변경됐나(content/git hash) → 변경됐으면 faithfulness 재검증.
- ✅ 안 바뀌었으면 추출·연결 결과 **재사용**, 바뀐 unit만 재처리. 원본 삭제되면 **참조하던 관계도 정리**.
- 상태로: `orphaned`(앵커 못 찾음) / `fresh`(span hash 동일 → 의미검증 생략) / hash 달라짐 → 재검증.
- ✅ hash 비교는 스크립트로 충분 → **비결정적 판단(모델)은 꼭 필요한 곳만.** (글 전체의 척추)

**⑤ NLI (Natural Language Inference)**
- 🔧 **교정.** "평가 기법, 사람이 판단할 단계로 분류"가 아님.
  NLI는 두 문장의 관계를 **모델이 3분류**하는 것: entailment(뒷받침) / contradiction(모순) / neutral.
  - Faithfulness: "주장 vs 원문 span"이 entailment인가 → 근거가 진짜 받쳐주는지 자동 판정.
  - Consistency: 두 근거가 contradiction인가 → 충돌 자동 감지.
  즉 NLI는 **관계 자동 판정기(앞단)**, 사람에게 넘기는 `disputed` 분류는 그 **뒤의 후속 흐름**. 둘은 다른 층.

---

## ❓ 궁금증 → 해소

- **Consistency의 "출처 다른 조합 우선 비교"?**
  같은 개념 근거가 2개↑면 **문서↔코드↔메신저처럼 출처가 다른 쌍부터** 대조.
  같은 출처 내 모순은 대개 편집 실수/중복(약한 신호), **다른 출처 간 불일치**가 진짜 신호(정책 변경·구현 미반영·팀 간 이견). → 노이즈 거르고 진짜 `disputed`(재시도 즉시실패 vs 3회 vs 2회)에 사람 시간을 씀.

## 🔁 도메인 안 가리는 패턴 (전이 가능)
1. **답을 만들지 말고 '믿을 수 있게' 만들어라.** AI는 매 질문에 답을 낸다 → 다 풀린 것 같지만, 그 답이 몇 점짜리인지 판단할 근거·환경이 없으면 신뢰가 없다.
2. **신뢰도는 연속 점수보다 '상태'로 이산화.** `fresh`/`stale`/`disputed`/`orphaned`. "몇 점 차이나야 문제냐"가 안 풀리는 건 연속 점수에 임계값 정답이 원래 없어서다.
3. **비결정적 판단은 꼭 필요한 곳만.** 잘 구조화된 곳은 모델 대신 hash·규칙으로 확정. 모델은 의미 판단에만.
4. **저장만 쌓지 말고 변경에 반응.** hash로 변경 감지 → 바뀐 것만 재검증, 삭제되면 참조도 정리.
5. **불확실성을 숨기지 말고 관리 가능한 상태로.** 자동 못 합칠 건 조용히 지우지 말고 양쪽 다 보존 + 상태 노출 → 사람은 진짜 문제 지점만 판단.
6. **처음부터 다 하려 하지 마라.** Coverage로 "무엇이 빠졌나"를 관찰 가능한 신호로 두고 보강 대상을 판단.

## 🎯 오늘 챙길 한 줄
> 내 eval/rubric 고민의 처방: **종합 점수 하나 대신 검증 가능한 원자 축으로 쪼개고**(근거 있나/모순 없나/최신인가), **점수 대신 상태로 이산화**하고, **자동 통과 못 한 것만 사람이** 본다.

## 🔮 미해결 / 다음에 팔 것
- 저자도 남긴 것: Coverage("무엇이 빠졌나")와 팀의 암묵적 별칭 이해 → 사람 맥락이 계속 필요.
- 내 적용: 지금 돌리는 에이전트 eval을 6축처럼 원자 축으로 분해 + 상태화(임계값 대신) 실험해보기.
- Canonicality 자동 누적 방지 — 주기적 임베딩 유사도 점검 + 모호한 것만 사람 승인, 실제 운영 주기는?
