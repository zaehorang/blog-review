# 올리브영 — 프레임워크 무관 통합 백오피스 (Vue Web Components)

## 🔑 한 줄 요약
> 프레임워크 경계를 넘나드는 공유 컴포넌트는 **파일에 비밀을 담지 말고, 실행 시점에 부모가 메모리로 직접 쥐여줘라** — 훔쳐가도 무용지물이 되게.

## 📌 무슨 글 (중립 요약)
- 올리브영 백오피스가 React/Vue/JSP로 나뉘어 있는데, 동일한 "상품정보 화면"이 세 시스템 모두 필요해 프레임워크마다 중복 개발해야 했다.
- iframe(SameSite로 세션 공유 차단)과 시스템 마이그레이션(과한 리스크·시간) 대신, Vue의 `defineCustomElement`로 웹 컴포넌트를 만들어 모노레포 → S3 → CDN으로 배포하고, 각 시스템이 커스텀 태그(`<goods-detail>`)로 불러 쓴다.
- 인증은 ①쿠키 재사용 ②axios 인스턴스 주입 ③토큰 프로퍼티 주입 3가지로 부모가 실행 시점에 넘겨주고, SSR/SEO는 포기하되 "로그인 이후" 화면에만 적용해 그 한계를 우회한다.

---

## 🧠 내가 이해한 것 → 교정 (오늘의 핵심)

**① `defineCustomElement`가 하는 일**
- 내 생각: 빌드하면 그냥 html 태그로 바뀌는 것 아닌가.
- 🔧 교정: 정적 HTML로 바뀌는 게 아니라 `HTMLElement`를 상속한 **진짜 커스텀 엘리먼트 클래스**가 나온다. 안엔 **Vue 런타임이 그대로 들어있어** 반응성·라이프사이클이 계속 돈다. 바뀌는 건 "쓰는 쪽의 계약"뿐 — React/JSP는 Vue를 몰라도 표준 태그 하나만 놓으면 됨. 비유: **통조림**(안은 Vue 요리, 뚜껑=인터페이스만 표준 규격).

**② Shadow DOM이 막는 방향**
- 내 생각: 컴포넌트 스타일은 shadow 안에 독립돼서, 필요한 스타일을 직접 찾아 입혀줘야 한다.
- 🔧 교정: 방향이 반대. 컴포넌트 자기 CSS는 `defineCustomElement`가 shadow 안에 **자동으로** 넣어줘서 부모와 안 섞인다(장점). 성가신 건 **"밖→안" 차단**: 부모의 전역 폰트·디자인 토큰이 shadow 경계를 못 넘어와서, 그건 **수동으로 shadow root 안에 다시 주입**해야 한다.

**③ 인증 전달 — "같은 메모리라서 된다"는 절반만 맞음**
- 내 생각: 같은 메모리에 올라가니 쿠키 정보를 바로 쓴다.
- 🔧 교정: 원인이 두 가지로 섞여 있었음.
  - **쿠키 재사용**은 브라우저가 HTTP 요청에 자동으로 쿠키를 싣는 것 — **같은 origin(도메인)**이면 되고 메모리와 무관.
  - **axios 인스턴스/토큰 프로퍼티 주입**이 진짜 "메모리" 얘기. 웹 컴포넌트는 iframe과 달리 **부모와 같은 JS 실행 컨텍스트(같은 window)**에서 돌아서, 함수·설정이 박힌 **살아있는 JS 객체를 참조로 그대로** 넘길 수 있다. iframe은 별개 `window`라 postMessage로 직렬화 가능한 데이터만 주고받을 수 있어 이게 불가능.
  - 💡 이게 "구조적 보안"의 실체: 실제 key·axios 인스턴스는 **파일에 문자열로 박제된 적이 없고**, 부모 메모리에서 살아있는 객체로만 존재하다가 실행 시점에 넘어옴 → CDN 주소를 훔쳐도 재료(부모 인스턴스)가 없어 무용지물.

**④ SSR/SEO를 포기해도 되는 이유**
- 내 생각(확인): 웹 컴포넌트는 JS가 실행된 이후에야 값이 채워지므로 SEO에 안 잡힐 수 있다.
- ✅ 정확. 크롤러는 최초 HTML(`<goods-detail></goods-detail>`)만 보면 빈 껍데기 → JS 실행 후에야 콘텐츠가 채워짐.
- 💡 한 단계 더: "로그인 이후" 화면이면 이 한계가 애초에 발동 안 함 — 크롤러는 로그인을 못 하니 그 페이지에 도달조차 못 함. **한계를 극복한 게 아니라, 한계가 무의미해지는 자리를 골라 쓴 것.**

## ❓ 궁금증 → 해소

- **"origin" 두 가지 뜻이 헷갈림** — CDN의 origin server(=S3, 캐시 미스 시 가져오는 원본 저장소)와 보안의 origin(=프로토콜+도메인+포트, CSRF/SameSite 판단 기준)은 완전히 다른 개념. DNS→엣지 라우팅(CDN)과 CSRF의 origin 검증(서버가 요청 헤더 판단)은 서로 무관한 별개 시스템.
- **CDN 동작** — DNS가 사용자 위치 기준 가장 가까운 엣지 IP 반환 → 엣지에 캐시 없거나 만료(TTL)면 오리진(S3)에서 가져와 서빙. 재배포해도 옛 캐시가 남는 문제는 **콘텐츠 해시 파일명**으로 해결 — URL 자체가 바뀌어 무조건 캐시 미스가 되게 하는 것 (TTL을 우회하는 게 아니라 TTL을 신경 안 써도 되게 만드는 것).
- **S3는 AWS 고유 상품명** — "오브젝트 스토리지"라는 일반 개념을 AWS가 부르는 이름. GCP는 GCS, Azure는 Blob Storage.
- **CSRF 방어** — 공격은 "로그인된 사이트 쿠키가 악성사이트발 요청에도 자동으로 실려서" 벌어짐. 방어는 CSRF 토큰(악성사이트는 못 읽음) 또는 Origin/Referer 헤더 검증.

## ⚖️ 세 가지 솔루션 비교

| | iframe | 시스템 마이그레이션 | Vue Web Components ✅ |
|---|---|---|---|
| 메커니즘 | 타 시스템 화면 단순 임베드 | 하나의 프레임워크로 통일 | 표준 커스텀 태그화 |
| 핵심 장점 | 가장 단순, 화면 독립 배포 | 아키텍처 통일성 | 프레임워크 종속 없음, 부모 자원 공유, 독립 배포 |
| 결정적 단점 | 세션 공유 차단(SameSite) | 수개월 대공사, 배보다 배꼽 | 초기 빌드 파이프라인 구성 필요 |

→ 최고점이 아니라 **치명적 실점이 없는 쪽**이 선택됨.

## 🔁 도메인 안 가리는 패턴 (전이 가능)

1. **엔지니어링은 최고의 정답이 아니라, 주어진 제약 속에서 치명적 실점이 없는 선택.** (iframe=보안 실점, 마이그레이션=시간 실점, 웹컴포넌트=둘 다 어중간하지만 기존 시스템 안 건드림)
2. **비밀은 파일에 박제하지 말고 실행 시점에 메모리로 주입.** 배포되는 산출물(JS 번들, 이미지 등)엔 민감정보를 담지 말고, 실행 환경이 그때그때 쥐여주게 — 유출돼도 무용지물이 되도록.
3. **기술적 한계는 없애려 하지 말고, 그 한계가 발동 안 되는 영역을 찾아 쓴다.** (SSR 불가 → SEO 필요없는 로그인 후 화면에만 적용)
4. **공유 모듈이 "같은 실행 컨텍스트인가"가 무엇을 넘길 수 있는지를 결정한다.** 같은 컨텍스트면 살아있는 객체(함수·클로저)까지 참조로 전달 가능, 다른 컨텍스트(iframe)면 직렬화 가능한 데이터만.

## 🎯 오늘 챙길 한 줄
> 공유 코드를 여러 환경에 흩뿌릴 땐 먼저 물어라 — **"이 조각이 도둑맞아도 무용지물인가?"** 비밀은 파일이 아니라 실행 시점 메모리에만 살게 하면 유출 자체가 무해해진다.
