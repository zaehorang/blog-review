# Nextree — 타입스크립트 파헤치기

## 🔑 한 줄 요약
> 타입은 컴파일 타임의 "약속"일 뿐이고 런타임엔 벗겨져 사라진다 — 그래서 체크(정적 분석)와 변환(코드 생성)은 서로를 막지 않고 독립적으로 굴러가며, 그 틈(외부 데이터·`as` 남용·인덱스 초과)은 Zod 같은 런타임 검증으로 메워야 한다.

## 📌 무슨 글 (중립 요약)
- TS 도입 이유 3가지(컴파일 타임 에러 검출/DX/자동 문서화), TSC 파이프라인(스캐너→파서→바인더→체커→이미터), 구조적 타이핑, 타입 추론을 소개.
- TS가 못 막는 런타임 에러 3종(외부 API 응답 불일치, `as` 오용, 배열 범위 초과)을 사례로 제시하고, `noUncheckedIndexedAccess`와 Zod 같은 런타임 검증 결합을 대안으로 짧게 언급.

## 🧠 내가 이해한 것 → 교정

**① 브라우저는 왜 JS만 이해해? 확장 시도는 없었나?**
- 💡 한 단계 더: 있었고 대부분 실패, 하나는 성공. Java Applet/Flash/Silverlight는 플러그인 기반이라 표준화·보안 문제로 전부 폐기. 성공한 건 **WebAssembly** — 2019년 W3C 4번째 웹 표준, JS를 대체가 아니라 "나란히" 실행되는 저수준 바이트코드(C/Rust/Go 컴파일 산출물). 단 DOM 직접 접근은 아직 안 돼서 JS가 glue 역할.

**② transpile과 type check, 왜 직렬(체크 통과해야 변환)이 아니라 따로 굴러가나**
- 🔧 교정: 정반대로 알고 있었음. 기본 tsc는 타입 에러가 있어도 JS를 emit함(`noEmitOnError`를 켜야 막힘) — 반복 개발을 안 막으려는 설계. 더 근본적으로 "타입 제거"는 문법적 변환이라 타입 정보 없이도 가능해서(→ esbuild/swc가 체크 없이 초고속 transpile만 하는 이유), 실무는 오히려 **transpile(빠름, 파일 단위)과 type check(느림, 전체 프로그램)를 의도적으로 분리해 병렬 실행**함(`tsc --noEmit`을 별도 프로세스로).
- 🔧 이어서: "실행해서 문제 생기면 검수(체크)가 잡아준다"도 틀림. 체크는 **정적 분석**이라 실행과 무관하게 소스코드만 보고 동작함 — 코드를 한 번도 안 돌려도 에러를 찾아냄. 실행 결과를 관찰해서 잡는 게 아니라, 저장하는 순간 독립적으로 같은 소스를 훑는 것.

**③ 스캐너→파서→바인더→체커→이미터, 이게 TS만의 구조인가?**
- ✅ 파이프라인 구성 이해는 정확. 다만 "체크하고 **안전하면** 이미터가 변환"은 오류 — 체커와 이미터는 별개 단계고 이미터는 체크 결과와 무관하게 emit함(②와 동일 지점).
- 💡 한 단계 더: 이건 컴파일러 이론의 표준 패턴(Lexer→Parser→Semantic Analysis→Codegen)이고 TS 전용이 아님. **정적 타입 언어(C/Java/Go/Rust/TS)는 파서와 코드생성 사이에 "의미 분석/타입 체크" 단계가 항상 끼고, 동적 타입 언어(순수 JS/Python/Babel)는 그 단계가 통째로 빠짐.** TS는 기계어까지 안 가고 JS에서 멈추는 소스-투-소스 트랜스파일러라서 IR/최적화 단계가 없는 상대적으로 단순한 파이프라인.

**④ 런타임 에러가 아예 안 날 수 있는 언어/로직이 있나? 서버 통신 없으면 괜찮을까?**
- 🔧 교정: "타입 에러 없음"과 "런타임 에러 없음"은 다른 질문. 완전히 0으로 만드는 범용 언어는 사실상 없음(0으로 나누기, 스택 오버플로우 등은 타입과 무관). 정리 증명 언어(Idris, Coq)는 이론상 가능하지만 항공전자·암호학 수준 극한 안전 분야 전용, 비용이 너무 큼.
- Rust/Haskell/OCaml은 TS처럼 타입을 완전히 소거하지 않고(제네릭 monomorphization, `Option`으로 null 자체를 타입에 편입) 훨씬 강한 보장을 주지만, 그래도 panic 같은 런타임 크래시는 남음.
- 서버 통신을 없애면 "타입 불일치로 인한" 에러는 크게 줄지만 0은 아님 — 서드파티 JS 라이브러리의 타입 정의(`@types/...`)가 실제와 다를 수 있고, 배열 인덱스·재귀 깊이 같은 순수 연산 버그는 타입 시스템과 무관하게 남음.

## ❓ 궁금증 → 해소

- **Zod가 뭔가?** → TS 타입은 컴파일하면 사라지니, "이 데이터가 진짜 이 타입 맞아?"를 **런타임에** 실제로 검사해주는 스키마 검증 라이브러리. `UserSchema.parse(data)`로 실제 값을 까보고 안 맞으면 그 자리에서 명확한 에러를 던짐.
- **`as`는 언제 쓰나?** → 정당한 쓰임: DOM 요소 좁히기(`getElementById(...) as HTMLInputElement`), `JSON.parse()`처럼 `any`가 된 값에 임시로 타입 지정, 서드파티 타입 정의 오류 우회, `as const`(오히려 타입을 더 좁혀 안전하게 만드는 용도), 마이그레이션 중 임시 땜빵. 위험한 쓰임: 진짜 호환 안 되는 타입끼리 억지로 우겨서 컴파일러 입을 막는 것 — 이게 글에서 경고한 그 패턴.
- **`z.infer<typeof Schema>`로 SoT가 된다는 게 이런 뜻?** → ✅ 맞음. 스키마 하나(Zod)를 원본으로 두면 TS 타입(`z.infer`)도 런타임 검증(`.parse()`)도 둘 다 거기서 파생되므로, 타입과 검증 로직을 손으로 따로 관리하다가 하나만 고치고 어긋나는 상황 자체가 구조적으로 불가능해짐.

## 🔁 도메인 안 가리는 패턴 (전이 가능)

1. **"체크"와 "변환"을 분리하면 반복 속도가 이긴다.** 정확성 검증(느림, 전체 범위)과 실행 가능한 산출물 생성(빠름, 부분 범위)을 한 파이프라인에 직렬로 묶지 않고 독립 프로세스로 병행하는 설계 — 빌드 도구뿐 아니라 CI(정적분석 vs 배포), 코드 리뷰(자동 머지 vs 사람 리뷰) 등 어디든 적용 가능한 트레이드오프.
2. **정적 분석은 실행을 관찰하지 않는다.** "실행 → 문제 발생 → 감지"가 아니라 "소스만 보고 독립적으로 판단"이라는 걸 헷갈리면 안 됨 — 린터, 타입체커, 정적 보안 스캐너 전부 같은 원리.
3. **SoT 패턴: 파생 가능한 걸 두 번 쓰지 않는다.** Zod처럼 스키마 하나에서 타입과 검증을 둘 다 뽑아내는 구조 — API 스펙(OpenAPI)에서 클라이언트 코드 생성하는 것도 같은 패턴.
4. **언어(도구)는 만들어질 때의 우선순위를 반영한다.** JS의 느슨함은 안정성을 몰라서가 아니라 "페이지가 절대 안 멈추게"라는 다른 목표를 최우선했던 설계 선택. 도구를 볼 때 "뭘 희생하고 뭘 얻으려 했나"를 먼저 물으면 이해가 빠름.

## 🎯 오늘 챙길 한 줄
> 타입은 컴파일 타임 약속이지 런타임 사실이 아니다 — 그 틈을 메우려면 검증 로직을 타입과 따로 관리하지 말고, 하나의 스키마에서 둘 다 파생시켜라(SoT).
