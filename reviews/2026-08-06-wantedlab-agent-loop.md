# 원티드랩 — 디자인 시스템 4.0을 에이전트 루프로 만들기

## 🔑 한 줄 요약
> 티켓→머지가 34.9일→3.9일이 됐지만 그 대부분은 **구현이 빨라진 게 아니라 기다림이 사라진 것**이고, 그걸 가능하게 한 건 똑똑한 프롬프트가 아니라 **판단(모델)과 절차(스킬)를 가르고, 검증을 산출물에 박아넣은 하네스**다 — 단, 그 검증이 사람에게 남아 있던 자리에서 비용이 조용히 디자이너에게 이전됐다.

## 📌 무슨 글 (중립 요약)
- iOS 디자인 시스템(SwiftUI 패키지 `Montage`, 컴포넌트 60개·릴리즈 146개)의 4.0 메이저 업데이트를, 작업을 하나씩 처리하는 대신 **처리 과정 자체를 파이프라인화**해 에이전트에 넘긴 기록.
- 루프: 디자이너 티켓(Figma 링크) → 에이전트가 브랜치·구현·문서재생성·Draft PR → TestFlight 업로드 → 채널에 QA 요청 → 디자이너 QA → 지적 나오면 다시 티켓. **개발자는 루프 안에 없고** 옆에서 머지만 누른다.
- 장치 4개: 스킬(절차 고정) / MCP(외부 연결, 디자인 시스템 자체가 MCP 서버) / 규칙 파일 4곳 / docstring 단일 소스 문서 파이프라인.
- 측정 결과와 함께 **측정이 어디까지만 가능했는지**(순수 구현시간 못 잼, 표본 34·28건)도 같이 적었다.

## 🧠 내가 이해한 것 → 교정 (오늘의 핵심)

**① "에이전트에게 같은 말을 두 번 하면 파일로 옮겨야 한다"**
- 내 생각: 두 번 말한 건 고정 컨텍스트로 두자.
- ✅ 맞음(저자 원문과 동일). 💡 다만 이 글의 값어치는 그 다음 한 겹 — **"어느 파일"** 을 4곳으로 쪼갠 기준에 있음.

  | 어디 | 배포 범위 | 기준 |
  |---|---|---|
  | `CLAUDE.md` | 저장소 → 팀 전원 | 이 저장소에서 일하는 누구에게나 참인 규약 |
  | 스킬 + 훅 | 플러그인 → 팀 전원 | 절차 + 그걸 타게 하는 가드를 **한 묶음**으로 |
  | 에이전트 메모리 | 내 머신만 | 저장소에 적으면 **남에게 강요가 되는 것** |
  | 예약 태스크 | 1회성 | 지금 한 번 돌릴 명세(5KB) |

- 가르는 질문: **"이걸 저장소에 적으면 남에게 강요가 되나?"** 저자 예시 — "커밋 전 현재 브랜치 확인"은 워크트리 여러 개 쓰는 본인에겐 필수지만 한 브랜치만 쓰는 팀원에겐 불필요 → 메모리로.
- 양쪽 실패가 다 있음: 개인 습관을 CLAUDE.md에 올리면 팀 전원이 쓸데없는 제약을 짊어지고, 공유 규칙을 메모리에 두면 팀원 결과물이 나와 갈라짐.

**② "절차는 스킬 말고 훅으로도 고정하면 이중 장치 아닌가"**
- 내 생각: 스킬도 결국 텍스트라 틀릴 수 있으니 훅으로 한 겹 더.
- 🔧 교정: **방향은 맞지만 그건 이중화가 아니다.** 저자의 훅이 하는 일은 *"git·배포는 맨손 명령 대신 스킬로 태우라"는 **안내를 끼워 넣는 것**"* — 차단이 아니라 텍스트 주입이다. 즉 훅도 스킬과 **같은 층**이고, "모델이 무시하면 무너진다"는 실패 모드를 공유한다(= 상관된 실패).
- 강제력의 층위:
  ```
  1. 프롬프트              매번 말해야 함. 잊으면 끝
  2. 파일(CLAUDE.md·스킬)   항상 로드되나 모델이 안 따를 수 있음
  3. 훅(안내 주입형)        자동 주입이지만 여전히 텍스트 → 모델 재량
  ──────────────────────── 여기까지 전부 "설득"
  4. CI 게이트 / 권한 차단   모델 재량 밖. 아예 못 함   ← 진짜 이중 장치
  ```
- 증거: `verify-docs`가 최근 100회 중 **7번 걸림.** 규칙은 CLAUDE.md에 적혀 있었는데도 7번 샜다는 뜻. 층 2·3이 완벽했다면 0이어야 함.
- 저자 교훈도 이 층 얘기: *"CI 게이트는 에이전트에게 특히 잘 듣습니다. 사람의 기억력과 성실함에 의존하지 않습니다."*
- **→ 내 아이디어의 강화판:** 훅을 *안내형*이 아니라 **차단형**으로(PreToolUse에서 호출 자체를 거부). 그래야 층 4로 올라간다.

**③ docstring을 SoT로 두고 문서·MCP를 파생시키기**
- 내 생각: 수정이 자주 일어나는 곳이 코드 파일이니 거기서 단일 원천으로 뽑아내는 게 좋다. 제약/대가는 있지만 그것도 규칙으로 에이전트가 지키게 하면 된다.
- ✅ 이유까지 정확. 💡 한 겹 더 정교하게: SoT를 고르는 기준은 **"어디가 거짓말을 못 하는가"**.
  - 코드 = 틀리면 컴파일이 깨지거나 동작이 틀어짐 → **진실에 강제로 묶여 있음** → 원천
  - 문서 = 틀려도 아무 일 없음 → 방치되면 조용히 썩음 → 파생
  - 방향이 반대면(문서가 원천, 코드를 손으로 동기화) 반드시 어긋난다.
- 🔧 "규칙으로 지키게 하면 된다"는 절반: 저자가 실제로 CLAUDE.md에 넣었지만 **그래도 7/100이 샜다.** 규칙(층 2) + 게이트(층 4) 둘 다 필요.
- 💡 반전: 저자는 당시 *"이 규칙들이 지속 가능할까"* 고민했는데 지금은 자산이 됨. **자동화 비율이 올라가면 "빡빡한 규약"의 손익분기가 뒤집힌다** — 사람에겐 비용인 제약이 에이전트에겐 전부 이득이므로.

**④ "검증과 구현을 나누자 — ML의 train/test split과 같은 원리"**
- ✅ 훌륭한 유추. 🔧 다만 글에 나온 분리는 **두 종류**이고 목적이 다르다.

  | | 무엇을 나누나 | 목적 |
  |---|---|---|
  | (a) preflight ↔ pr | **읽기 ↔ 쓰기** | **피해 반경 축소.** 잘못 판단해도 아무것도 안 저지름 |
  | (b) 구현 ↔ 검증 정보원 | **텍스트 스펙 ↔ 렌더된 픽셀** | **독립성.** 같은 정보원 보면 같은 오해 반복 |

- train/test split은 **(b)에 대응**. (a)는 오히려 최소 권한(least privilege) 쪽.
  ```
  학습 데이터로 평가   = 구현에 쓴 스펙 텍스트로 검증 → 통과가 뻥튀기
  data leakage        = 검증 기준이 구현 입력과 같은 출처
  held-out set        = 시뮬레이터 픽셀 (구현 중 안 본 축)
  프로덕션 성능        = 디자이너 QA (최종 홀드아웃)
  ```
- **"overfit한 구현"의 실제 모습**도 글에 있음: 에이전트가 티켓 문구엔 맞췄는데 화면 수치는 안 맞음 → 네 개 전부 1차 QA 지적. **스펙 텍스트에 오버핏.**
- ②와 같은 원리: **겹치는 두 장치는 성질이 달라야 한다.** 텍스트+텍스트 ✗, 텍스트+기계 ✓.

**⑤ "코스트가 없어서 못 하던 걸 AI로 하게 된 것 — 대기 시간이 사라진 것과 같은 맥락"**
- ✅ 이 글의 진짜 주장을 잡음. 💡 대기가 사라진 이유는 두 갈래:
  1. **착수 비용이 낮아져 미룰 이유가 없어짐** — 예전엔 "붙어야 하는 일"이라 다른 업무와 경쟁하며 큐에 쌓임. 지금은 한 줄 던지면 되니 큐가 안 생김.
  2. **병렬화** — 워크트리로 61초 간격 두 개, 사람 없는 저녁 8시 예약 실행.
- 🔧 "그럼 다 AI로 하면 빨라지네"로 읽으면 6.2절이 반박: 대기 보정 후 실제 향상은 **2.0배**, 그마저도 대부분 "리뷰가 빨리 돌아간 정도"(PR 생성→머지 41.8h→21.9h).
- **→ 더 정확한 형태: 저비용화가 늘리는 건 처리 속도가 아니라 "시도 횟수"다.** 증거 = TestFlight 27회, 7월에만 18회. 한 방에 빨리 끝낸 게 아니라 **많이 돌린** 것. 값이 싸지면 되풀이가 가능해지고, 되풀이가 가능하면 완성도 기준이 올라간다.
- 6.3의 자백이 여기 붙음: **티켓 만드는 습관 자체가 바뀜**(일괄 적재 → 필요할 때). 도구가 빨라지면 사람의 일하는 방식이 바뀌고, 그게 지표에 섞여 도구 효과와 분리가 안 된다.

**⑥ QA 요청 메시지 — 비판적으로 읽힌다 (내가 먼저 걸린 지점)**
> "다른 작업이 밀려있다보니 이번 작업은 거의 80% AI 작업으로 이루어져서 오류가 있을 수 있습니다. 평소보다 조금 더 꼼꼼히 살펴봐 주시면 감사하겠습니다."

- 내 반응: 수정은 개발자 역할이었으면 책임도 개발자가 져야 하는 것 아닌가. 디자이너에게 넘기는 느낌.
- ✅ 저자도 정확히 같은 단어로 예상했음 — *"변명처럼 들릴 수도 있고 품질에 대한 책임을 떠넘기는 것 같이 보일 수도"*. 예상하고도 보냈고, 글에선 **잘한 선택으로 회고**한다. 그 회고가 쟁점.
- 🔧 날을 정확히: QA를 맡기는 것 자체는 전가가 아님(디자이너 QA는 원래 상시 역할). 문제는 문장의 **세 겹** 중 뒤 둘.

  | 조각 | 성격 | 판정 |
  |---|---|---|
  | "AI로 작업했습니다" | 공개 | ✅ 숨기는 것보다 훨씬 낫다 |
  | "다른 작업이 밀려있다보니" | 변명 | ⚠️ 상대가 알 필요 없는 내 일정 사정 |
  | "평소보다 더 꼼꼼히" | **부담 이전** | ❌ 원인은 내 쪽인데 비용을 상대 기준선에 얹음 |

- 🔧 **저자의 이지선다가 이지선다가 아님.** {숨긴다} vs {밝히고 더 부탁한다}로 놓았지만 세 번째가 빠졌다 — **{밝히고 + 내 쪽 검증을 올린다}**. 그리고 이건 이상론이 아니라 **저자가 2주 뒤에 직접 구현한 것**(예약 태스크의 픽셀 샘플링 대조, PR 본문 검증 결과 표, 리뷰봇 대응 루프).
- 💡 정상참작: 이 메시지는 **7/16**, 하네스가 아직 얇던 시기. 문제는 저자가 이걸 임시방편이 아니라 *"이 선택이 루프를 오래 굴러가게 한 이유"* 로 회고한다는 점 — **"이 시점부터 잘 됐다" → "이 선택 덕분이다"로 건너뛴 귀인 오류.** 6절에서 숫자에는 그토록 엄격했던 사람이 자기 판단에는 그 엄격함을 안 썼다.
- 방증(결정적이진 않음): 네 개 **모두** 1차 QA 지적 → 두 바퀴째. Select·Segmented는 나흘 뒤 또. 7월 TestFlight 18회. 단 **3.0 시기 통과율이 글에 없어 비교 기준선이 없다.**

**⑦ "QA 에이전트나 중간 검수 단계를 하나 뒀으면 되지 않았나"**
- ✅ 맞고, **저자 자신의 규칙 위반**이다. QA 지적은 전부 숫자였음(`icon size 18`, `gap 6`, `height 40`, `radius 12`) — 취향이 아니라 스펙 대 렌더 결과 대조, 기계가 제일 잘하는 종류.
- 부품은 다 있었음: 시뮬레이터 MCP(스크린샷), Figma MCP(스펙), `preflight`라는 "읽기만 하고 결과만 반환" 패턴, 그리고 3.3절 예약 태스크에 **절차까지 이미 써놨음** — *"스크린샷 찍고 색상 픽셀을 샘플링해서 스펙 값과 대조할 것"*.
- 그런데 스킬 7개에 없다 = **일회성 명세에 묻힘.** 바로 다음 문단의 저자 규칙: *"반복적으로 필요해지는 게 보이면 일회성 명세에 묻어두지 말고 스킬이나 CLAUDE.md 같은 공유 규칙으로 올려야 합니다."*
- **진단 — preflight에 축이 하나 비었다.** 검사 항목(공개 API 변경/docstring 누락/쇼케이스 예제/보호 브랜치/기존 PR)이 전부 *코드가 규약을 지켰나*. **"화면이 스펙과 맞나"가 없음.** 게이트 있는 데선 안 터지고 없는 데서 터졌다.
- 🔧 한계도 정확히: 자동 대조는 **비교 기준이 확정돼야** 작동. 이 글엔 기준이 흔들린 기록이 둘 — 작업 브랜치가 구 토큰 체계라 "스펙에 적힌 토큰명을 그대로 믿지 말라"(두 번 걸림), QA 티켓 컬러 토큰명이 개편 이전 기준. 스펙이 낡으면 기계는 **자신 있게 틀린 답**을 낸다. 그러니 결론은 "QA 에이전트가 디자이너를 대체"가 아니라 **"기계가 잡을 걸 먼저 걸러 사람이 판단에만 집중하게"**.
- **결정적 사실:** 2.2절 PR의 검증 결과 표 + before→after 표는 **이미 존재했다.** 다만 **디자이너가 지적한 뒤에** 나왔다(검증 가능한 형태의 QA 티켓이 끌어낸 산출물이라서). 문제는 능력이 아니라 **타이밍** — 같은 표를 QA 요청 *전에* 만들었으면 그 왕복이 통째로 사라진다. 저자가 디자이너 공으로 돌린 그 메커니즘을 **사람 입력에 의존하지 말고 스킬로 고정했어야** 했다.

## ❓ 궁금증 → 해소

- **breaking change = 뭔가를 없애는, 영향 큰 이벤트?**
  → 🔧 **판정 기준이 "영향의 크기"가 아니다** ([Breaking change & semver](../concepts/breaking-change.md)). 이 글에 붙는 부분:
  - **조용한 breaking**(동작·기본값 변경)이 왜 여기서 문제냐 — 앞의 것들은 컴파일러가 잡아주는데 이건 화면만 달라진다. QA 티켓이 *"height 40, radius 12 — 이 수치가 맞는지 확인"* 형태였던 이유.
  - `preflight`의 첫 검사가 "공개 API가 바뀌었는지"인 것도 같은 맥락 — *"public 인터페이스가 명시적이니 무엇이 breaking change인지 판단할 근거가 코드 안에 있다"*.
  - Montage는 **MIT 공개 저장소** → "쓰는 곳"을 grep으로 셀 수 있는 범위가 사내로 한정됨. 되돌릴 수 없으니 **사람이 먼저 합의**해야 하고, 그 합의는 티켓이 만들어지기 **전에** 끝나 있어야 한다(티켓이 곧 에이전트의 명세 전부이므로).

- **디자이너의 "outlined 쓰는 게 1개일까요?"가 무슨 뜻?**
  → 변종(variant) 사용처 개수를 묻는 것. 판단이 직관과 반대라 헷갈렸음:
  - **적으면 → 없애고 solid로 통일** (그 변종이 값을 못 함, 고칠 호출부도 적어 지금이 기회)
  - **많으면 → 남긴다** (마이그레이션 비용 크고, 많이 쓴다는 게 필요하다는 증거)
  - 즉 **지우는 비용과 남기는 명분이 둘 다 사용처 수에 비례**해서 방향이 갈리지 않는다.
  - 💡 "몇 군데 쓰나"는 에이전트가 grep으로 답할 수 있다. 못 하는 건 세는 게 아니라 **그 숫자를 놓고 무게를 재는 일**. 사람 자리를 가르는 선은 "정보 수집"이 아니라 **"트레이드오프 판정"** 에 그어져 있다.
  - 💡 그리고 이 대화에 쓰인 시간은 6절의 "대기 구간"에 들어간다. **줄여야 할 대기(누가 붙어주길 기다림)와 지켜야 할 대기(합의)가 한 덩어리로 측정되고 있다.**

- **docstring이 뭔가?** ([docstring](../concepts/docstring.md))
  → 이 글에서의 위치: **docstring이 단일 진실**. `make` → DocC 아카이브 → ①문서사이트 Markdown ②MCP용 JSON 인덱스로 갈라짐. 같은 뿌리라 어긋날 수 없고, 하나만 갱신하면 `verify-docs` CI가 막는다.
  - *"에이전트가 쓴 docstring이 며칠 뒤 공개 문서의 문장으로 게시되는데, 그 사이에 사람이 옮겨 적는 단계가 하나도 없습니다."*
  - 3.4절의 제약들이 전부 여기서 나옴: `public` 빼먹지 마라 / 파일명=타입명 / 관련 타입 한 파일에 / 물결표 이스케이프(`~~`가 취소선으로 해석돼 깨짐). → **⑦번 패턴("빡빡한 규약의 손익분기")의 실제 사례.**

- **스킬 7개가 어떤 순서로 도나?**
  → 평평한 목록이 아니라 **계층 + 별도 트랙**이다.
  ```
  👤 "[티켓] 해결하고 PR 생성해"
     ├─① montage-branch          티켓에서 브랜치명·base 확인
     ├─② 구현  ⚠️ 스킬 없음        ← "판단은 모델에게"의 영역
     ├─③ montage-pr  ◀ 오케스트레이터
     │     ├─ montage-preflight  (읽기만: API변경·docstring·예제·브랜치·기존PR 수집)
     │     ├─ montage-commit     (diff → Conventional Commits)
     │     ├─ 문서 재생성 (docstring→DocC→md/json)
     │     ├─ push
     │     └─ Draft PR 생성      ◀ 에이전트는 여기까지. 일부러 그은 선
     └─④ montage-blueprint-deploy  버전 도출→빌드번호→archive→TestFlight
        → 채널에 QA 요청(MCP)
  👤 PR 검토 → 머지
     ↺ QA 지적 → 새 티켓 → ①부터              ← 루프는 여기서 돈다
  ═══ 머지가 쌓인 뒤 사람이 판단해 한 번만 ═══
     ⑤ montage-release  릴리즈·태그 → auto-deploy-docs → 문서사이트 저장소 원격 트리거
  ═══ 완전 독립 ═══
     montage-icon-sync  아이콘 바뀔 때만
  ```
  - 💡 **커밋 메시지가 사람용이 아니다.** Conventional Commits(`fix:`/`feat:`/`BREAKING CHANGE:`)가 곧 PATCH/MINOR/MAJOR이고, `blueprint-deploy`의 첫 단계 "버전 도출"이 **거기서 뽑는다.** docstring이 문서이자 MCP 입력이었던 것과 같은 패턴 — **사람용 산출물을 기계 입력으로 재사용하면 둘이 어긋날 수 없다.**

## 🐛 겪은 문제 & 해결

- **PR 스킬에 검증이 섞여 있었다** → 만든 **바로 다음 날** `preflight`를 분리. 큰 그림이 있어서가 아니라 *"한 번 데어보고"* 나눔. 저자: *"읽는 일과 실행하는 일을 갈라놓으면, 에이전트가 잘못 판단했을 때 그 피해 반경이 좁아집니다."* (스킬은 3월 말~6월 중순, 여섯 번의 커밋으로 하나씩 늘었다 — 설계도 없음)
- **스펙을 믿었다가 두 번 데임** → 작업 브랜치 소스가 구 토큰 체계라 Figma 스펙의 토큰명이 실제와 불일치. 해결: 예약 태스크 명세에 *"토큰명을 그대로 믿지 말고 실제 자산의 색상값을 대조해서 매핑하라"* + 확인된 매핑 표를 통째로 박아넣음.
- **순수 구현 시간을 못 쟀다** → 티켓 '진행 중' 전이가 실제로는 **브랜치 푸시 시점**에 찍혀서 착수가 아니라 마무리였음. 첫 커밋 시각도 못 씀(다 해놓고 커밋한 경우 다수). 4.0에선 28건 중 **5건이 값이 음수**. 해결 못 하고 **한계로 공개**.

## 🔁 도메인 안 가리는 패턴 (전이 가능)

1. **겹치는 두 장치는 성질이 달라야 이중화다.** 텍스트(프롬프트·규약파일·안내형 훅) 위에 텍스트를 얹으면 상관된 실패다. 진짜 두 번째 겹은 **재량 밖의 기계적 차단**(CI 게이트, 권한 거부). 같은 원리가 검증에도 적용 — 구현과 검증이 **같은 정보원**을 보면 같은 오해를 두 번 한다(스펙 텍스트 ↔ 렌더된 픽셀).
2. **SoT는 "거짓말을 못 하는 쪽"으로 정한다.** 코드는 틀리면 깨지니 진실에 강제로 묶여 있고, 문서는 틀려도 아무 일 없으니 썩는다. 묶여 있는 쪽을 원천으로, 안 묶인 쪽을 파생으로. 방향이 반대면 반드시 어긋난다.
3. **비용을 남에게 넘기면 그 비용은 지표에서 사라진다.** 34.9→3.9일은 **개발자 쪽 시계**다. 디자이너가 흡수한 QA 왕복은 어디에도 안 잡힌다. 자동화 성과를 볼 때 항상 물어라 — **줄어든 건가, 옮겨간 건가? 옮겨간 쪽은 재고 있나?**
4. **검증 부담은 산출물에 붙이고 사람에게 붙이지 마라.** "80% AI라 꼼꼼히 봐주세요"는 불안 전파(정보량 0, 상대가 뭘 다르게 할지 모름). "X를 분기했으니 medium/large 수치를 보세요 + 픽셀 대조 결과는 표에" 는 **주의 라우팅**(상대 부담이 오히려 준다).
5. **저비용화가 늘리는 건 속도가 아니라 시도 횟수다.** 실제 처리 향상은 2.0배인데 TestFlight는 27회 돌았다. 값이 싸지면 되풀이가 가능해지고, 되풀이가 가능하면 완성도 기준이 올라간다 — "코스트가 없어서 못 하던 것"이 열리는 자리.
6. **도구가 바뀌면 사람의 일하는 방식도 바뀌고, 그게 지표에 섞인다.** 티켓 일괄 적재 습관이 사라진 것처럼. 그래서 개선 폭은 **숫자 하나가 아니라 범위로** 말하는 게 정직하다(1.26~2.0배).
7. **자동화 비율이 올라가면 "빡빡한 규약"의 손익분기가 뒤집힌다.** 파일명=타입명, `public` 필수 같은 제약은 사람에겐 비용이지만 에이전트에겐 전부 이득(탐색 불필요, 읽을 범위가 닫힘, breaking 판정 근거가 코드 안에, 자가 대조 기준 존재).
8. **읽기와 쓰기를 가르면 실수의 반경이 줄어든다.** `preflight`(수집만) ↔ `pr`(실행). 최소 권한 원칙의 에이전트 판.
9. **파이프라인은 "무엇을 할지"가 정해진 뒤부터만 굴러간다.** breaking 범위 합의처럼 트레이드오프 판정이 필요한 건 티켓이 만들어지기 전, 루프 밖에서 끝나 있어야 한다. 정보 수집은 위임 가능, 무게 재기는 아니다.
