# 여기어때 — 늙어버린 당신의 AI (자산 노화 감사)

## 🔑 한 줄 요약
> 모델은 이름 한 줄로 갈아타지만 **그 위에 쌓은 자산(설정·지침·메모리)은 안 따라온다.** 게다가 낡아도 **에러를 안 내서** 손해가 조용히 누적된다 → 시간 주기가 아니라 **신모델 GA를 트리거로** 감사하고, 애초에 **튜닝값 0**으로 만들어 검진할 것 자체를 줄여라.

## 📌 무슨 글 (중립 요약)
- Claude 5 출시를 트리거로 팀 저장소를 감사, 전사 배포되던 `settings.json`에서 **두 줄 삭제**.
  `DISABLE_ADAPTIVE_THINKING=1`(신모델은 무시 / 구모델엔 역효과), `effortLevel: "high"`(기본값이 이미 high라 실효 0, Opus 4.7 사용자만 강등).
- 지침 문서의 "생각 과정을 숨겨라"도 thinking 분리 후 세대에선 "추론을 줄여라"로 오독될 수 있어 문구 정밀화.
- 대응: **모델 진화 runbook + 동기 불변식 + 리뷰 상기** 3겹. 그리고 개인용 "3분 검진".

## 🧠 내가 이해한 것 → 교정 (오늘의 핵심)

**① "모델이 바뀔수록 쌓인 자산을 **주기적으로** 검증해라"**
- 🔧 방향은 맞는데 **"주기"가 아니라 "트리거"**. 시간 주기(매달 1일)는 **내 규율**에 의존하지만, 글이 세운 건 **밖에서 빌린 트리거** — 신모델 GA, 벤더 마이그레이션 가이드 발행, 팀 감사 공지. 습관을 내 의지가 아니라 **외부 이벤트**에 걸었다는 게 설계의 핵심.

**② "디폴트 프로퍼티도 바뀌고, 동작 자체도 바뀐다"**
- ✅ 맞음. 두 줄이 정확히 그 두 갈래였음 — `effortLevel`=**기본값이 바뀐 케이스**, `DISABLE_ADAPTIVE_THINKING`=**동작 자체가 바뀐(무시하는) 케이스**.
- 💡 근데 글의 진짜 축은 *무엇이* 낡았나가 아니라 ***찾을 수 있나***:
  - **명시 의존** — 모델명·가격이 박힘 → `grep` 한 방. 그나마 나은 쪽.
  - **암묵 의존** — "얘 말 많으니 짧게 답하게 하자" 류. **파일 어디에도 "모델 X 기준"이라 안 적혀 있음** → 세대가 바뀌어도 아무도 재검토를 떠올리지 못함. ← **이쪽이 진짜 위험.**

**③ "이를 막을 워크플로우를 하나 두는 것"**
- ✅ 맞음 / 💡 **왜 "하나"로는 안 됐는지**가 포인트. 각 겹이 앞 겹의 구멍을 막음:
  1. **runbook(목록)** — 어디를 볼지. → 문제: **목록은 만든 순간부터 낡는다.**
  2. **동기 불변식** — 세대 가정 있는 파일을 고치면 **같은 커밋에서** 목록 갱신 강제. 1의 부패를 막음.
  3. **리뷰 상기** — 2를 사람이 까먹으니, 리뷰에서 `thinking`·`effort`·모델명이 보이면 체크.
- 글이 **자기 한계를 숨기지 않은 게** 좋았음: *"모델 의존 여부는 기계적으로 판별할 수 없어 자동 차단 린트로는 만들 수 없다"* → 최종 방어선은 결국 사람이 도는 전체 감사.

**④ "프로젝트 세팅할 때 어떤 모델 기반인지 기록"**
- ✅ 정확. 글의 **기준선(baseline)** 그 자체. 강력한 이유는 — **암묵 의존을 명시 의존으로 강제 승격**시키기 때문. 개별 파일엔 "모델 X 기준"이라 안 적혀 있어도, 저장소에 기준선이 박혀 있으면 `기준선 ≠ 현재 모델`인 순간 **전체가 재검토 대상**이 됨. ②의 최대 위험에 대한 대응책.

**⑤ "모델명을 하드코딩 하지 않기"**
- ✅ 맞음. + 글은 **서브에이전트 정의의 모델 고정**도 같이 지적(세션 모델 상속). 하드코딩은 설정 파일에만 숨는 게 아님.

**⑥ "기본값을 추가할 때는 의심" ← 오늘의 핵심 교정**
- 🔧 **방향이 정확히 반대.** 원문은 *"**튜닝값은 공식 기본값으로 충분한지** 먼저 의심"*. 의심 대상은 기본값이 아니라 **기본값을 덮어쓰려는 내 튜닝값**.

  | | 기본값에 맡김 | 내가 명시함 |
  |---|---|---|
  | 세대 전환 시 | 벤더가 **자동 갱신** | **내가 유지보수해야 할 자산** |
  | 검진 비용 | 0 | 매 세대 문서 대조 |

  → **"설정을 안 적는 것"도 하나의 설정 전략.** 값을 명시하는 순간 편의가 아니라 **부채**로 등록됨. 그래서 원칙은 "새 모델 나왔으니 설정을 바꾸자"가 아니라 **"바꿀 설정이 없게 만들자"**. (*"가장 싼 검진은 검진할 것을 만들지 않는 것"*)

**⑦ "현재 모델용 기법·프롬프팅도 나중엔 레거시"**
- ✅ 맞음 / 💡 근데 **레거시(무해)를 넘어 안티패턴(유해)**으로 뒤집힘 →

  | 한 세대의 모범 기법 | 다음 세대에선 | 출처 |
  |---|---|---|
  | "단계별로 생각하라"(CoT 강제) | 불필요·**성능 저해** | OpenAI reasoning 가이드 |
  | "Be concise / 짧게 답해라" | **과도 압축** 유발 | GPT-5.x 가이드 |
  | "끝나면 스스로 검증해라" | Opus 5는 알아서 검증 → **과잉 검증** | Anthropic 마이그레이션 가이드 |

  **함정: 셋 다 도입 당시엔 "모범 기법"이었다.** 잘못 넣은 게 아니라 **잘 넣은 게 독이 된 것** → "누가 실수했나"로는 못 잡고 **트리거 기반 감사로만** 잡힘.

**⑧ 내가 통째로 빠뜨린 축 — 메모리도 늙는다**
- 설정과 메모리는 **묶여 낡는 대상이 다름**:

  | | 무엇에 묶이나 | 위험 |
  |---|---|---|
  | 설정·지침 | **모델 세대** | 구세대용 튜닝이 신세대에 무효/역효과 |
  | 메모리 | **사실의 시점** | 그때 참이던 게 지금도 참이라고 **재주장** |
- 글의 자기고발: 과거 감사 메모가 "설정값이 고지 없이 강제된다"고 지적해뒀는데, **이번 감사가 그 설정을 지웠는데도 메모는 여전히 현재형으로 지적을 들고 있었다.** 감사 안 돌렸으면 미래 세션은 **이미 풀린 문제를 여전한 문제로** 읽었을 것.
- 처방이 반직관적인데 정확함: **틀린 기억은 지우지 말고 "정정 마커"로 교체.** 지우면 같은 오판 재발 시 막을 게 없지만, `"그 주장은 틀렸다 — 재주장 금지"`가 남아 있으면 그게 **방어선**이 됨.

## ❓ 궁금증 → 해소

**Q. "벤더"가 뭐야?** ([벤더](../concepts/vendor.md))
→ 논지에서 중요한 이유는 *"**벤더가 먼저** 말하고 있습니다"* — "우리가 유별나서 감사한 게 아니라, **모델 만든 회사가 공식 문서로 '이 지시 지워라'를 이미 내놓고 있다**"는 근거로 쓰임. 남은 건 그 문서를 **자기 자산에 적용하는 절차**뿐인데, 그 절차를 가진 팀이 드물다는 게 글의 간극.

**Q. runbook의 "3등급 나눔", 특히 3등급이 이해가 안 감. 어떤 플로우?**
→ 등급의 기준은 위험도가 아니라 ***"신모델이 나왔을 때 이걸 어떻게 찾아낼 것인가"* = 탐지 방법**.

| 등급 | 정체 | 탐지 | 예 |
|---|---|---|---|
| **1 · 명시 의존** | 모델명·버전·가격이 문자열로 박힘 | **grep이 찾아줌** | `"model": "claude-opus-4-6"`, 서브에이전트 `model: opus`, 위키의 "$15/1M 토큰" |
| **2 · 암묵 의존** ⚠️ | 모델명 0글자, 특정 세대 성향 대응 값·문구 | **grep 불가 — 목록만이 찾음** | `effortLevel:"high"`, `max_tokens:4096`, "짧게 답해라" |
| **3 · 비의존 확인** | **봤고, 세대 무관하다고 판정 끝** | **찾을 필요 없음** | 커밋 규칙, 파일명 규칙, 산출물 |

- **2등급의 함정:** 파일엔 `effortLevel: "high"` 딱 한 줄만 있고 **"왜 넣었는지"가 어디에도 없음.** 두 세대 뒤 사람은 "왜 있지? 지워도 되나?" 단서가 없어 **그냥 놔둠**(에러도 안 나니까). → **목록에 적는 행위 자체가 유일한 방어** = 암묵 의존을 명시 의존으로 승격. 여기어때가 지운 두 줄, **둘 다 2등급**.
- **3등급이 왜 필요한가 (제일 안 와닿았던 것):** 무관해도 **"무관하다"고 쓴다.** 이유는 —

  > **"목록에 없다"의 의미를 하나로 못박기 위해서.**

  | | 3등급 없을 때 | 3등급 있을 때 |
  |---|---|---|
  | 목록에 없는 파일 = | ❓ 안 봤거나 / 봤는데 무관하거나 | ✅ **무조건 "아직 안 봄"** |

  침묵이 두 뜻이면 매 감사마다 전 파일을 **다시** 판정해야 함. 3등급이 "봤는데 무관"을 목록 안으로 흡수하면 밖에 남는 건 **오직 미확인**뿐 → **사각지대를 셀 수 있게 됨.** 글이 *"목록 등재가 빠진 파일은 여전히 사각지대"*라고 쓸 수 있는 것도 이 덕분(3등급 없으면 몇 개인지 알 수가 없음).
- **감사 한 바퀴:** grep 스윕(1등급 회수) → 목록 순회하며 2등급만 **벤더 공식 문서 대조** → 3등급 스킵 → 목록에 없는 신규 파일 판정 → 변경 있으면 기록·리뷰·배포 / 없으면 **기준선만 갱신**.
  목록이 없으면 이 2번이 설정 파일을 한 줄씩 "이거 왜 있지"부터 되짚는 **"막막한 탐색"**이 됨.
- **3등급은 영구 면제권이 아님.** 도장은 **그날의 내용물**에 찍힌 것. `AGENT.md`에 "짧게 답할 것" 한 줄 들어오는 순간 **2등급으로 강등**돼야 하고, 그걸 잡는 게 **동기 불변식**.
  → **3등급 = 사진 / 동기 불변식 = 사진이 현실과 어긋나지 않게 붙잡는 끈.**

**Q. 2등급은 정말 전부 grep이 안 되나?**
→ 아니. `thinking`·`effort`·`budget`·`max_tokens` 같은 **벤더 고유 파라미터명**은 검색됨. 글이 리뷰 체크 항목을 *"thinking·effort·모델명 같은 튜닝이 보이면"*으로 잡은 게 이 지점. **진짜 안 잡히는 건 자연어 지시문**("짧게 답해라") — 이건 사람 눈밖에 방법이 없음.

## ⚖️ 감사에서 나온 두 줄 비교

| | `DISABLE_ADAPTIVE_THINKING=1` | `effortLevel: "high"` |
|---|---|---|
| 도입 의도 | thinking 예산 고정 → 동작 예측 가능하게 | 팀 전체 effort 통일 |
| 신모델에서 | **무시됨** (Opus 4.7+ / Claude 5) | 공식 기본값이 이미 high → **실효 0** |
| 구모델/일부에서 | 4.6 계열에 고정량 thinking 강제 → **비용·속도 악화** | Opus 4.7(기본 xhigh) 사용자는 **한 단계 강등** |
| 손해 청구 방식 | 비용·속도 | 일부 사용자의 **출력 품질** |
| 에러 | **없음** | **없음** |

→ **둘 다 몇 달간 "문제를 일으키지 않는 것처럼 보였다."**

## 🔁 도메인 안 가리는 패턴 (전이 가능)

1. **"에러를 안 내는 고장"이 제일 오래 산다.** 코드는 전제가 깨지면 컴파일 에러·테스트 실패로 알려주지만, **설정·프롬프트·문서·메모리는 낡아도 그냥 조용히 적용된다.** 재검토 트리거가 없으면 영원히 안 발견. → 자산을 볼 때 물어라: *"이게 틀렸을 때 누가 나한테 알려주나?"* 답이 "아무도"면 **감사 대상.**
2. **탐지 가능성으로 분류하라 — 위험도가 아니라.** `grep으로 잡힘 / 목록에만 있음 / 볼 필요 없음`. 진짜 관리 비용은 **가운데 하나**에 몰려 있고, 목록이라는 장치는 그것 하나 때문에 존재한다.
3. **"확인했고 문제없음"을 기록하라.** 침묵이 "미확인"과 "확인 후 무해" 둘 다를 뜻하면 매번 처음부터 다시 한다. **후자를 명시적으로 기록해야 전자를 셀 수 있다.** (테스트 skip 사유, 보안 점검 N/A, 코드리뷰 "확인함" 전부 같은 구조)
4. **기본값에 맡기는 것도 전략이다.** 값을 명시하는 순간 그건 편의가 아니라 **내가 유지보수할 부채**. 벤더 기본값은 세대마다 **공짜로 갱신**된다. → *"바꿀 설정이 없게 만들자."*
5. **오늘의 모범 기법이 내일의 안티패턴이 된다.** 잘못 넣어서 생긴 문제가 아니라 **잘 넣은 게 시간이 지나 독이 된 것**이라, 책임 추적으로는 절대 안 잡히고 **주기적 재검증으로만** 잡힌다.
6. **트리거를 밖에서 빌려라.** 내 규율에 걸린 점검은 언젠가 끊긴다. **벤더 릴리스·GA 공지 같은 외부 이벤트**에 걸면 남이 대신 알람을 울려준다.
7. **틀린 기억은 지우지 말고 정정 마커로 덮어라.** 삭제하면 같은 오판이 재발할 때 막을 게 없다. `"이건 틀렸다 — 재주장 금지"`가 다음 방어선이 된다.
8. **자동화 못 하는 걸 자동화한 척하지 마라.** *"기계적으로 판별할 수 없어 린트로는 못 만든다"*고 쓴 뒤 사각지대를 명시한 게 이 글의 신뢰도. **한계를 적어두면 그건 사각지대가 아니라 알려진 위험**이 된다.

## 🎯 오늘 챙길 한 줄
> 내가 쌓은 설정·지침·메모리를 볼 때 물어라 — **"이게 낡으면 누가 나한테 알려주나?"** 아무도 안 알려준다면, 지우거나(튜닝값 0) 적어둬라(목록 등재). 그 둘 말고 셋째 선택지는 **모르고 늙는 것**뿐이다.
