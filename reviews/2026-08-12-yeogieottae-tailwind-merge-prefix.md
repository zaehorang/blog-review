# 여기어때 — 항공 프론트엔드 구축기 (3/10): prefix를 붙이자 tailwind-merge가 조용히 깨졌다

> [2편 — Vue2 디자인 시스템을 React로 옮기기](2026-08-11-yeogieottae-vue2-to-react-design-system.md)에서 `className` 확장을 열어둔 대가가 실제로 청구된 직속 후속편이다.

## 🔑 한 줄 요약
> **도구의 확장 지점을 쓰면 앞선 선택을 지킬 수 있지만, 확장한 순간 그 도구가 숨겨 관리하던 규칙과 유지보수 책임까지 물려받는다.**

## 📌 무슨 글 (중립 요약)
- 공용 라이브러리의 스타일을 사용하는 앱과 격리하려고 Tailwind 클래스에 `yf-` prefix를 붙였더니, `tailwind-merge`가 충돌을 인식하지 못해 `className` 오버라이드가 조용히 실패했다.
- prefix를 떼고 병합한 뒤 다시 붙이던 기존 해법은 문자열 조작이 필요하고 커스텀 유틸리티를 처리하지 못했다. 새 구현은 prefix가 붙은 클래스를 그룹과 충돌 관계로 직접 등록했다.
- 격리·Tailwind 자산·`className` 확장을 모두 유지한 대신, 클래스 분류표를 손으로 관리하고 누락 시 에러 없이 실패하는 책임이 남았다.

---

## 🧠 내가 이해한 것 → 교정

**① 문제 상황 — prefix 때문에 merge가 안 됐다**

- 내 이해: 다른 곳에서도 쓸 라이브러리라 class name 충돌을 막으려고 prefix를 붙였다. 그런데 `bg-` prefix가 있어야 뒤의 클래스가 적용되는 merge 기능이 동작하는 듯하다.
- ✅ **라이브러리에 prefix가 필요한 이유는 맞다.** 사내 디자인 시스템이 이미 `yf-`를 전제로 삼고 있었고, 이를 빼면 사용하는 앱의 Tailwind 클래스와 겹칠 수 있다.
- 🔧 **`bg-`가 없어서가 아니다.** `yf-bg-red-500` 안에도 `bg-`는 있다. 다만 이 글의 `tailwind-merge` 설정은 `yf-`가 앞에 붙은 형태를 기존 배경색 분류와 연결하지 못했다. Tailwind는 CSS를 생성하지만 별도 도구인 병합기는 이를 모르는 문자열로 본다.
- 🔧 **뒤의 클래스를 적용하는 주체도 Tailwind 자체가 아니라 `tailwind-merge`다.** 실제 CSS를 덮는 게 아니라, 같은 역할의 앞쪽 클래스 문자열을 제거한다. 분류하지 못해 둘 다 남으면 HTML의 class 순서가 아니라 생성된 CSS 규칙의 순서가 승자를 정한다.
- → 범용 동작은 [tailwind-merge](../concepts/tailwind-merge.md)에 분리.

**② 대안 네 개 — 무엇을 지키기 위해 무엇을 포기하지 않았나**

| 선택 | 잃는 것 |
|---|---|
| prefix 제거 | 사용하는 앱과의 스타일 격리 |
| `twMerge` 제거, `clsx`만 사용 | `className`에 의한 예측 가능한 덮어쓰기 |
| CSS-in-JS로 전환 | Vue2의 Tailwind 클래스 문자열을 그대로 옮긴 이점 |
| **prefix + `twMerge` 유지** | 채택 — 대신 분류표 유지 책임을 짐 |

- 🔧 `clsx`가 인라인 스타일을 주입하는 건 아니다. `clsx`는 조건에 따라 클래스 문자열을 이어 붙일 뿐 충돌을 해소하지 않는다. 덮어쓰기를 보장하지 못하니 `bgColor`, `textColor` prop을 따로 뚫고 내부에서 인라인 스타일로 우회하게 된 것이다.
- ✅ 결국 **앞선 선택의 이유가 아직 유효했기 때문에 선택 자체를 버리지 않고, 도구의 확장 지점을 찾았다.** 2편에서 여백 prop을 없애고 `className`을 열었던 결정을 이번 편에서도 유지했다.

**③ 1세대 해법 — prefix를 떼고 합친 뒤 다시 붙이기**

- 내 이해: 기존 라이브러리의 `prefixTwMerge`가 prefix를 떼고 병합한 뒤 다시 붙인다. 이 작업이 반복되면 병목이 된다.
- ✅ 렌더마다 `join → replace → split → map → join`을 거치는 비용은 실제 한계다. variant가 있을 때는 `hover:yf-bg-*`처럼 **조건 뒤, 유틸리티 앞**에 prefix를 다시 넣어야 해서 문자열 처리도 단순하지 않다.
- 🔧 하지만 글에서 더 결정적인 한계는 **정확성과 적용 범위**다. `replace`는 클래스 값 안의 동일 문자열까지 지울 수 있고, prefix를 떼어도 `yds6-TypoUi-14` 같은 사내 유틸리티는 기본 분류표에 없어서 여전히 병합되지 않는다. 성능 최적화보다 **문제의 절반만 푼 해법**이라는 게 교체 이유에 가깝다.
- → 1세대는 병합기를 **속였고**, 2세대는 병합기에게 우리 분류 체계를 **가르쳤다.**

**④ 같은 이름 앞부분이어도 역할이 다르다 — `classGroups` 세분화**

- 내 이해: 커스텀 클래스를 직접 등록하면서 같은 prefix 안에서도 역할이 다른 경우를 세분화해, 같이 적용돼야 하는 클래스가 하나만 남지 않게 했다.
- ✅ 정확하다. `yf-text-center`, `yf-text-14`, `yf-text-ellipsis`, `yf-text-content-primary`는 모두 `yf-text-`로 시작하지만 각각 정렬·크기·오버플로·색상이다. 한 그룹에 넣으면 서로를 지우므로 역할별 그룹으로 갈라야 한다.
- 🔧 다만 이 역할은 `conflictingClassGroups`가 아니라 **`classGroups`를 올바르게 세분화하는 것**이다. 같은 접두어가 아니라 **실제 CSS 역할**이 분류 기준이다.
- 💡 `isAny` 같은 catch-all 색상 규칙을 마지막에 등록해야 `ellipsis`를 먼저 색상으로 삼키지 않는다. 확장 API를 썼다고 자동으로 안전해지는 게 아니라, **등록 순서가 분류 우선순위**가 된다.

**⑤ CSS 속성과 유틸리티가 1:1이 아니다 — 그룹 간 충돌은 단방향**

- 질문: `p-16`은 padding 하나인데 네 방향을 포함하고, 같은 그룹은 아닌 `px-8`과 서로 영향을 준다는 게 무슨 뜻인가?
- 해소: `classGroups`는 **같은 역할**, `conflictingClassGroups`는 **서로 다른 역할 사이에서 뒤의 것이 앞의 효과를 완전히 없애는 관계**다.

```ts
twMerge('yf-px-8 yf-p-16') // → 'yf-p-16'
// 뒤의 전체 16이 앞의 좌우 8까지 완전히 덮는다.

twMerge('yf-p-16 yf-px-8') // → 'yf-p-16 yf-px-8'
// 전체 16 중 위아래는 필요하고, 좌우만 8로 바뀐다. 둘 다 남아야 한다.
```

- → 충돌은 대칭이 아니다. `p`는 앞의 `px`를 지울 수 있지만, `px`가 앞의 `p`를 지우면 위아래 정보까지 사라진다. `rounded → rounded-t → rounded-tl`처럼 부분 영역이 계층을 이루는 곳도 같은 문제다.

**⑥ 여기서 말하는 variant는 무엇인가**

- Tailwind variant는 클래스를 **언제 적용할지** 나타내는 수식어다: `hover:`, `disabled:`, `mobile:`. `hover:yf-bg-red-500`에서 `hover:`가 variant다.
- 버튼의 `variant="primary"` prop은 컴포넌트가 제공하는 디자인 종류라는 별개 의미다. 이름만 같다.
- 커스텀 breakpoint는 별도 등록하지 않아도 됐다. 병합기가 `mobile`의 의미를 아는 게 아니라, 앞에 붙은 수식어 묶음이 같은지를 비교하기 때문이다.

## 🐛 겪은 문제 & 해결

- **증상:** 기본 `yf-bg-button-primary`에 `className="yf-bg-red-500"`을 얹어도 클래스가 둘 다 남았다. 빌드·타입 에러 없이 CSS 생성 순서에 따라 어떤 스타일은 바뀌고 어떤 것은 안 바뀌었다.
- **원인:** prefix가 붙은 커스텀 클래스가 병합기의 분류표에 없었다.
- **해결:** 문자열에서 prefix를 떼지 않고, `classGroups`에 실제 CSS 역할을 등록하고 `conflictingClassGroups`에 전체↔부분의 단방향 관계를 기록했다. 팀 사용처에서는 복잡성을 `tw` 템플릿 태그 뒤로 숨겼다.
- **남은 위험:** 새 유틸리티 등록을 빠뜨려도 같은 문제가 조용히 재발한다. 자동 생성 방법은 아직 없다.

## 🔁 도메인 안 가리는 패턴 (전이 가능)

1. **선택의 이유가 여전히 유효하면, 문제 때문에 선택부터 버리지 말고 도구의 확장 지점을 찾아라.** prefix·Tailwind 자산·`className` 확장 중 하나를 버리는 건 문제를 없애는 대신 앞선 결정의 이득도 없앤다. 다만 전부 지키는 비용이 분류표 소유라는 사실까지 같이 계산해야 한다. ([2편](2026-08-11-yeogieottae-vue2-to-react-design-system.md)의 **"확장 지점을 막지 말고 판단 기준을 줘라"**에서 열린 구멍의 실제 청구서.)

2. **이미 있는 해법을 찾되, 이름이 아니라 해결 범위를 대조하라.** 기존 `prefixTwMerge`는 같은 증상에 대한 프로덕션 해법이었지만 커스텀 유틸리티까지는 못 풀었다. "있다"와 "내 문제를 전부 푼다"는 다르다. → 기존 해법 확인 → 한계 확인 → 부족한 부분만 확장.

3. **도구를 커스텀하면 도구가 숨겨 관리하던 내부 모델까지 소유한다.** prefix 옵션은 세 글자짜리 설정처럼 보였지만, 병합기가 가진 클래스 분류·우선순위·단방향 충돌표를 함께 물려받게 했다. 확장 코드는 한 번 쓰지만 분류표는 새 유틸리티마다 갱신해야 한다.

4. **이름의 공통부분보다 실제로 건드리는 효과를 기준으로 분류하라.** `text-*`라는 모양은 같아도 정렬·색상·크기는 독립적이고, `p`와 `px`라는 모양은 달라도 효과가 겹친다. 좋은 분류는 문자열 모양이 아니라 **무엇을 지우고 무엇과 공존해야 하는가**로 검증한다.

5. **에러 없는 확장은 누락 감지 장치가 필요하다.** 등록하지 않은 새 클래스는 컴파일도 타입 검사도 통과하고 오버라이드만 조용히 실패한다. ([AI 자산 노화](2026-08-07-yeogieottae-ai-asset-aging.md)의 **"에러를 안 내는 고장이 제일 오래 산다"**, [2편](2026-08-11-yeogieottae-vue2-to-react-design-system.md)의 무효 클래스와 같은 생존 조건.) 이 글은 `tw`로 사용법은 숨겼지만, 분류표 누락을 잡을 자동화는 아직 남겼다.
