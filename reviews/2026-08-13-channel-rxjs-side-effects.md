# 채널톡 — RxJS로 우아하게 사이드 이펙트 통제하기

## 🔑 한 줄 요약
> **비동기 인터페이스의 완료는 첫 응답이 아니라, 그 인터페이스가 약속한 모든 사이드 이펙트가 끝난 시점이어야 한다.**

## 📌 무슨 글 (중립 요약)
- 채널톡 웹 SDK는 boot API 응답을 전체 boot 완료로 간주해, 아직 진행 중인 소켓 연결이 뒤이은 `shutdown → boot`와 충돌하는 타이밍 버그가 있었다.
- 개별 방어 코드를 추가하는 대신 epic·middleware·컴포넌트·서비스에 흩어진 흐름을 RxJS effect로 모으고, 상태 저장은 Redux에서 Zustand로 바꿨다.
- 각 공개 인터페이스를 스트림으로 직렬화하고 실제 `complete`와 구독 해제를 생명주기 경계로 삼아 순서·취소·자원 정리를 함께 통제했다.

---

## 🧠 내가 이해한 것 → 교정

### ① boot는 API 요청 하나가 아니라 사이드 이펙트의 연쇄다

- 내 이해: `boot 요청 → JWT 저장 → 게이트웨이에서 소켓 주소 조회 → 소켓 연결 → JWT로 authenticate`까지 이어진다.
- ✅ 맞다. API 응답은 전체 작업의 중간 지점일 뿐이고, 글에서 요구하는 boot 완료는 소켓 연결과 인증까지 끝난 시점이다.
- 🔧 새 boot는 단순히 항상 shutdown API부터 호출한다기보다, **이전 생명주기를 정리한 뒤 새 생명주기를 연다.** `shutdown`은 JWT·store·socket뿐 아니라 실행 중인 스트림의 구독 해제까지 책임진다.
- → 범용 스트림 모델은 [RxJS](../concepts/rxjs.md), 장기 연결과 인증은 [WebSocket](../concepts/websocket.md)에 분리.

### ② 고객에게 열린 인터페이스라 호출 순서를 예측할 수 없다

- 내 이해: 공개 SDK이므로 고객사가 boot를 중복 호출하거나 `boot → shutdown → boot`를 빠르게 호출하는 상황도 내부에서 안전하게 처리했어야 한다.
- ✅ 정확하다. 로그인 상태·설정 변경이나 컴포넌트 생명주기에 따라 같은 인터페이스가 연달아 호출될 수 있고, 이는 금지된 사용법이 아니다.
- 🔧 첫 boot가 실제로 완료된 뒤 문제가 난 것이 아니다. SDK가 **API 응답 시점에 너무 일찍 완료됐다고 알렸지만**, 첫 boot의 소켓 작업은 여전히 뒤에서 실행 중이었다.
- 💡 그래서 타이밍에 따라 재현 여부가 달라졌다. 뒤의 shutdown이 먼저 JWT를 지우면 첫 소켓 인증이 실패하고, 그렇지 않으면 겉으로 정상처럼 보이는 race condition이었다.

```text
Boot A: API 응답 ───────── 소켓 연결 ─ authenticate
              ↑ 완료라고 오판
Shutdown:       JWT/store 초기화
Boot B:         API 요청 ─────────── 소켓 연결
```

### ③ complete는 작업의 경계를 표현한다

- 내 이해: 파이프라인을 하나의 실행 단위로 보고 stream complete를 완료 상태로 판단한다.
- ✅ 이번 개편의 핵심이다. 각 호출을 스트림으로 만들면 이전 스트림의 complete 뒤에 다음 호출을 실행하도록 직렬화할 수 있다.
- 🔧 `complete`가 올바른 완료 시점을 자동으로 찾아주지는 않는다. 소켓 인증까지를 boot 스트림에 포함하는 것처럼, 팀이 인터페이스의 약속을 직접 파이프라인 경계로 표현해야 한다.
- 💡 계속 메시지를 받는 소켓 구독은 무한 스트림일 수 있다. boot의 연결·인증 완료와 이후 장기 메시지 구독을 구분하고, 후자는 shutdown에서 구독 해제하는 식으로 생명주기를 설계한다.

### ④ RxJS, Combine, AsyncStream은 어디까지 같은가

- 내 이해: 셋 모두 비동기 이벤트 흐름을 통제하고 이해하기 쉽게 정리하는 용도가 비슷하다.
- ✅ 큰 분류에서는 맞고, RxJS와 Combine의 반응형 스트림 모델이 특히 가깝다.
- 🔧 `AsyncStream` 하나가 RxJS 전체에 대응하지는 않는다. `AsyncStream`은 지속적인 값을 `AsyncSequence`로 소비하는 기본 도구에 가깝고, Swift structured concurrency는 Task의 부모·자식 관계와 취소 범위를 구조화한다.
- → RxJS의 `concatMap`, `mergeMap`, `switchMap`, `exhaustMap`은 단순 변환 도구가 아니라 직렬·병렬·전환 취소·중복 무시라는 **동시성 정책**을 고르는 연산자다.

### ⑤ 좋은 분리는 파일 수가 아니라 흐름의 소유자를 명확하게 한다

- 내 이해: UI 관련 로직은 컴포넌트에 남겨도 되지만, 컴포넌트는 파이프라인에 의도만 전달하고 내부에서 어떤 로직이 발생하는지 알 필요가 없다.
- ✅ 맞다. 컴포넌트는 `boot` 실행과 상태 관찰만 알고, 채널 조회·JWT 저장·게이트웨이 요청·소켓 인증 순서는 effect가 소유한다.
- 🔧 기존에도 코드는 역할별 파일에 분리되어 있었다. 문제는 한 액션의 흐름이 epic, middleware, 컴포넌트, 서비스에 파편화되어 **전체 순서의 주인이 없었다는 것**이다.
- → 개별 로직이 빠진 게 아니라, “소켓 인증까지 boot다”, “다음 호출은 전체 완료를 기다린다” 같은 **오케스트레이션과 시간적 계약**이 코드에 빠져 있었다.

### ⑥ Redux보다 RxJS가 간소화됐다는 말의 정확한 범위

- 내 이해: Redux보다 RxJS에서 이벤트 정의가 간소화됐다.
- 🔧 둘은 직접 대체 관계가 아니다. Redux는 상태 변경 모델이고 RxJS는 이벤트·비동기 흐름 모델이다. 실제 전환은 `Redux + redux-observable → RxJS effect + Zustand`였다.
- ✅ 기존에는 액션 타입·생성 함수·epic·reducer를 연결해야 했지만, 새 구조는 effect 안에서 흐름을 실행하면서 Zustand 상태를 동기적으로 바꿀 수 있어 연결 코드가 줄었다.
- → [미들웨어](../concepts/middleware.md)와 [Redux·Zustand·Jotai](../concepts/frontend-state-management.md)의 역할을 분리해 볼 것.

### ⑦ 메모리 이점은 자동이 아니라 명시적 정리 경계에서 온다

- 내 이해: 구독과 해제가 스트림으로 정의돼 예외·취소 처리와 메모리 관리에 이점이 있다.
- ✅ 구독의 주인과 종료 지점이 명확해졌다는 방향은 맞다.
- 🔧 RxJS도 구독을 해제하지 않으면 누수된다. 이 구조의 이점은 정상 종료는 `complete`, 실패는 `error`, 외부 취소와 shutdown은 구독 해제로 모으고, 해제 시 파이프라인이 붙들던 참조와 리소스를 연쇄적으로 정리할 수 있다는 데 있다.

## 🐛 겪은 문제 & 해결

- **증상:** 첫 boot의 소켓 인증이 JWT 없이 실패하고, 초기화된 상태로 게이트웨이 요청을 무한 재시도했다.
- **직접 원인:** boot API 응답을 전체 완료로 오판해 첫 boot의 후속 소켓 작업과 뒤의 `shutdown → boot`가 병렬 실행됐다.
- **구조 원인:** 하나의 공개 인터페이스가 만든 사이드 이펙트가 여러 계층에 흩어져 완료·취소·순서의 소유자가 없었다.
- **해결:** 비즈니스 흐름을 RxJS effect로 모으고, 각 인터페이스 호출을 실제 stream complete 기준으로 직렬화했다. Zustand는 흐름 중간의 동기적 상태 변경을 맡고 shutdown은 실행 중 구독 해제까지 맡았다.

## ⚖️ 비교표

| 역할 | 기존 | 개편 후 |
|---|---|---|
| 비동기 흐름 | Redux action과 epic·middleware·서비스에 분산 | RxJS effect의 한 pipe에 순서대로 표현 |
| 상태 변경 | action dispatch → middleware → reducer | Zustand store를 흐름 안에서 동기 변경 |
| 완료 기준 | boot API 응답 | 소켓 연결·인증까지 포함한 stream complete |
| 다음 호출 | 후속 작업과 겹칠 수 있음 | 이전 스트림 완료 뒤 실행 |
| 정리 | 상태와 소켓 위주 | 상태·소켓·실행 중 구독까지 해제 |

## 🔁 도메인 안 가리는 패턴

1. **공개 인터페이스는 정상 호출만이 아니라 호출 순서의 불확실성까지 계약에 포함한다.** 호출자를 통제할 수 없을수록 중복·연속·취소 호출에도 내부 상태가 일관돼야 한다.

2. **비동기 작업의 완료를 첫 응답과 혼동하지 않는다.** 함수가 시작한 후속 작업이 남아 있다면 외부에 완료를 알리기 전에 성공·실패·취소 범위를 먼저 정의한다.

3. **순서 버그가 반복되면 호출부의 방어 코드보다 작업의 소유자와 생명주기 경계를 찾는다.** `if (isBooting)`은 한 증상을 막지만 흩어진 사이드 이펙트의 완료 기준은 복구하지 못한다.

4. **연산자 선택은 구현 취향이 아니라 제품 정책이다.** 기다릴지(`concatMap`), 병렬 실행할지(`mergeMap`), 이전 것을 취소할지(`switchMap`), 새 것을 무시할지(`exhaustMap`)는 공개 인터페이스의 약속이어야 한다.

5. **역할별 분리와 실행 흐름의 응집은 함께 필요하다.** 컴포넌트·서비스를 나눴더라도 한 기능의 전체 실행을 설명하려고 파일 여러 개를 추적해야 한다면 오케스트레이션은 여전히 흩어져 있다.
