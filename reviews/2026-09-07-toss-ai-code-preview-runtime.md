# 토스 — AI가 만든 코드가 어드민이 되기까지 (Preview Runtime)

## 🔑 한 줄 요약
> 브라우저에 없는 "파일시스템 + 패키지 설치 + 빌드"를 흉내 내는 대신 — **비싼 작업(패키지 빌드)에 조합의 지문(해시)을 찍어 미리 서버에서 한 번만 만들어두면**, AI 생성 코드도 "설치"가 아니라 "다운로드"만으로 1.3초 만에 화면이 된다.

## 📌 무슨 글
- 토스 사내 어드민 제작 플랫폼 **TOI** — AI가 자연어 요청으로 React 어드민 코드를 생성.
- 그 코드를 브라우저에서 즉시 실행해 Preview로 보여주는 **런타임**을 어떻게 만들었나.
- 6개월간 439개 프로젝트 / 2,418개 페이지. Preview 첫 화면 **47초 → 1.3초**.

---

## 🧠 내가 이해한 것 → 교정 (핵심)

**① HMR을 "트랜잭션 커밋처럼 동작"으로 이해, admin이라 무시 가능하다고 판단**
- 🔧 **두 개념을 한 덩어리로 봤다.** 별개다.
  - **HMR**: 바뀐 모듈만 그래프에서 찾아 교체 + 화면 상태(입력값·스크롤) 보존. 목적은 개발 중 빠른 피드백. → 토스는 **안 씀.** 매번 iframe을 통째로 교체.
  - **트랜잭션 커밋**: HMR이 아니라 **에러 처리 전략.** 새 빌드가 터지면 반영 안 하고 마지막 정상 iframe 유지 = "성공한 것만 커밋".
  - → 토스는 HMR을 **버리고**(전체 교체) 트랜잭션식 롤백만 취함. 방향 판단("admin은 빠르게 볼 이유 없음")은 맞았고, 두 개를 합쳐 본 게 교정 포인트.
- 💡 iframe 통째 교체의 숨은 이득: 그 안 모든 모듈 인스턴스(싱글턴 포함)가 새로 생성 → 이전 실행의 상태 오염 걱정이 없다. (내가 던진 "싱글턴 고려" 직감과 연결됨)

**② "AI는 만드는 건 잘하지만, 뭐가 필요/불필요한지 판단·정의하는 건 사람 몫"**
- ✅ **이 글의 진짜 주제.** AI가 React 코드를 쏟아내는 건 이미 해결. 남은 문제는 전부 "그 코드를 **어디서 어떻게 실행 가능하게 만들 것인가**"라는 인프라 설계 판단. HMR 버리기, 빌드를 브라우저로 옮기기, 반복 비용을 변경 시점으로 미루기 — 다 사람 결정.

**③ "각 도구가 뭘 풀고 뭐가 가능/불가능한지 알고 도입하는 능력 + AI가 그 도구를 쓰게 만드는 능력"**
- 💡 이 글에서 구체적으로: esbuild-wasm(초고속, 파일시스템 없음), Sandpack(편하지만 매번 패키지 다운로드 47초), import map(브라우저 표준, 이름→URL). **각각의 제약을 정확히 알았기에** "esbuild는 내 코드 번들만 / 패키지는 미리 서버에서 Vite로 / 연결은 import map" 이라는 분해가 나옴. 도구 한계를 모르면 이 분해가 안 된다.

**④ "S3에 미리 빌드된 걸 두고, 필요 시 그 링크로 네트워크 요청하는 건가?"**
- ✅ 맞음. iframe 실행 중 `import 'antd'` → import map이 S3 URL로 치환 → 브라우저가 HTTP GET → 완성된 `antd.js` 응답. **"날것 재료 받아 요리" → "완성된 요리 받기".** `Cache-Control` + URL에 해시가 박혀 있어(content-addressed) 캐시를 영원히 잡아도 안전.

**⑤ "미리 빌드 + 해시로 같은 환경이면 그대로 받아오기, 설치가 아닌 다운으로"**
- ✅ 최종 이해 정확. 덧붙임: **일이 없어진 게 아니라 옮겨졌다.** 빌드는 여전히 일어남 — 다만 "매 Preview마다"가 아니라 "새 조합이 처음 등장할 때 1번". 대부분의 요청은 이미 처리된 조합이라 사실상 공짜.

## 🐛 겪은 문제 & 해결 (운영에서 마주친 것)

| 방식 | 얻는 것 | 잃는 것 |
|---|---|---|
| 서버에서 빌드 → 브라우저로 배포 | (빠를 것 같지만) | **격리 실패** — 한 사용자의 빌드 에러/무한루프가 서버 리소스를 먹고 무관한 다른 사용자에게 전파 |
| 브라우저마다 빌드 | **격리** 확보 (각자 독립 환경) | **속도** — 매번 패키지 다운로드+설치 47초 |
| **토스: 브라우저 빌드 + 패키지 미리 서버에서** | 격리 + 속도 둘 다 | 조합 관리 복잡도(→ packageSetHash로 흡수) |

## 📚 이 글로 정리한 개념 (concepts/로 분리)
- [패키지 매니저와 lockfile](../concepts/package-manager-lockfile.md) — `package.json`은 범위 선언, `yarn.lock`은 정확한 버전 스냅샷, `node_modules`는 펼쳐진 트리. 핵심은 **재현성**.
- [번들러](../concepts/bundler.md) — webpack/Vite/Rollup/esbuild/Rspack. "빠름 vs 기능 풍부함" 트레이드오프. esbuild는 엔진, Vite는 완제품.
- [import map](../concepts/import-map.md) — 브라우저 표준. `'react'` 같은 이름을 URL로 잇는 전화번호부. 번들 없이 외부 의존성 연결.
- [내용 주소화 (content-addressing)](../concepts/content-addressing.md) — 키를 내용으로부터 계산. 내용이 1바이트 바뀌면 키가 바뀜을 **보장**. git 커밋 해시, Docker 레이어, 캐시 버스팅이 같은 원리.

**이 글에서 왜 중요한가:** `packageSetHash` = 패키지 조합의 내용 주소. 이 하나로 "전에 빌드한 적 있나?"를 O(1)에 판별 → 빌드 스킵 + 캐시 영구화. 47→1.3초의 절반이 여기서 나온다.

## 🔁 도메인 안 가리는 패턴 (전이 가능)
1. **비싼 작업을 "요청 시점"에서 "변경 시점"으로 민다.** 대부분의 요청은 변화가 없으니, 변화가 있을 때만 계산하면 나머지는 공짜가 된다. ([증분 빌드](../concepts/incremental-build.md), CDN 캐시 버스팅과 같은 모양)
2. **비싼 결과물에 "내용의 지문(해시)"을 찍고, 지문이 같으면 재사용한다.** 이미지 디코딩 캐시, 빌드 캐시, Docker 레이어, 메모이제이션 전부 이 구조. URL을 키로 쓰면 "같겠지" 하고 믿는 것, 내용 해시는 "다르면 반드시 키가 바뀜"을 보장 → 캐시 영구화 가능.
3. **두 극단이 각각 하나씩 실패하면, 각 극단의 성공 조건만 떼어 조합한다.** (서버 빌드=격리 실패 / 브라우저 빌드=느림 → 브라우저 빌드로 격리, 패키지는 서버에서 미리 만들어 느림 제거)
4. **격리는 "새로 만들고 통째로 교체"가 제일 단순하다.** 부분 갱신(HMR)은 의존성 그래프를 추적해야 해 복잡하고 깨지기 쉽다. 상태 보존이 정말 필요할 때만 그 비용을 낸다. ([Nextree 웹소켓](2026-07-30-nextree-websocket-chat.md)의 "신호만 보내고 재조회"와 같은 결 — 복잡한 부분 동기화 대신 통째로 다시.)
5. **AI가 "만드는 문제"가 풀리면 병목은 "실행 가능하게 만드는 인프라"로 이동한다.** 도구 각각의 제약을 정확히 알아야 그 조합 설계가 나온다.
