# Google — AI 코딩 에이전트 하네스 엔지니어링

## 🔑 한 줄 요약
> 벤치마크 점수 대신 "이 상황에서 이 행동을 했는가"를 재는 유닛테스트를 쌓아라 — 그 테스트는 모델이 바뀌어도 남는 자산이 되고, 모델이 강해질수록 오히려 그걸 지키려고 붙여둔 하네스(프롬프트·툴 제약)는 가지치기할 수 있다.

## 📌 무슨 글 (중립 요약)
- 종합 벤치마크(Terminal-Bench 등)는 점수 변화만 보여줄 뿐, 왜 실패했는지(과신·검증 누락·환각)는 설명 못 함.
- 대안: [행동 평가](../concepts/behavioral-evaluation.md) — 특정 상황에서 특정 행동을 했는지를 예/아니오로 판정하는 로컬 유닛테스트.
- 하네스 엔지니어링 3단계: **Evaluate**(행동 평가 작성) → **Iterate**(평가 스위트를 가드레일 삼아 프롬프트 자동 최적화) → **Guard**(배치로 합산 통과율을 추적해 회귀 방지).
- 개발 초기(dogfooding) 단계엔 복잡한 평가 체계보다 직접 써보며 감을 잡는 걸 우선하라고 함.

---

## 🧠 내가 이해한 것 → 교정

**① 벤치마크 vs 행동 평가**
- 내 생각: 벤치마크는 모델 전체 평가 스코어, 행동 평가는 우리가 기대하는 특정 행동을 잘하는지에 대한 스코어. 결국 결과를 반복 시도하거나 모델을 바꿔서 얻는 것보다, 원하는 행동을 한 번에 잘 하게 만드는 게 핵심이다.
- 🔧 교정: 앞부분(벤치마크=전체 점수, 행동 평가=특정 행동 점수)은 정확함. 다만 뒷부분은 글의 실제 대비가 아니다. 글이 대비하는 건 "재시도 vs 원샷 성공"이 아니라 **"점수는 바뀌었는데 원인을 설명 못 하는 것(벤치마크) vs 어떤 구체적 행동의 유무를 바로 짚는 것(행동 평가)"**이다. "모호한 프롬프트에 되묻는가", "완료 선언 전에 validator를 돌렸는가" 같은 예시는 한 번에 성공했는지가 아니라 **특정 행동을 했는지**를 본다.
- ✅ 맞음: 벤치마크 스코어나 모델 능력은 잘못된 상황이 생기면 의미 없는 숫자고, 우리 코드베이스·상황에서 판단돼야 하며 그 형태가 unit test라는 것. 글 마지막 문장("It needs an evaluation harness that keeps it honest")과 정확히 같은 결론.

**② 개발 초기 단계 (dogfooding)**
- 내 생각: 처음부터 복잡한 eval 프로세스를 만들지 말고, 팀 내에서 써보고 기준을 잡아라. 에이전트가 자체 코드베이스를 읽거나, 보일러플레이트를 처리하거나, 자체 마크다운 렌더러를 쓰거나, 개발자 태스크를 실행할 수 있는 환경부터 만들어라.
- ✅ 맞음. 원문 그대로다 — "Until you have built an agent capable of dogfooding its own codebase, handling boilerplate, writing its own markdown renderer, and executing routine developer tasks" 전에는 공식 평가가 불필요하다는 게 "dogfooding precedent" 섹션의 요지.

**③ eval의 목적**
- 내 생각: eval은 기존 것을 지키는 도구라기보다, 앞으로 나아갈 때(forward progress) 퇴행을 막기 위한 도구다. 견고한 하네스는 원하는 방향으로 빠르게 나아가게 하고, 결정도 빠르게 만든다.
- ✅ 맞음. 원문 "giving you unshakeable confidence that a new prompt tweak, tool schema change, or model upgrade did not make the agent holistically worse"와 CI/CD 가드레일 비유가 정확히 이 얘기. 다만 "결정도 빠르게" 부분은 원문에 직접 있는 문장은 아니고 💡 스스로 뽑아낸 확장 — 가드레일이 있으면 변경을 두려워하지 않고 더 빨리 실험할 수 있다는 논리적 귀결이라 타당하다.

**④ 모델이 바뀌어도 남는 구조 (스스로 도달)**
- 내 생각: 중요한 건 모델이 발전할 때마다 바뀌는 구조가 아니라, 우리 컨텍스트 안에서 필요한 행동·테스트를 정의해 하나씩 쌓는 것 — 그러면 모델이 바뀌어도 우리가 원하는 방식으로 에이전트가 돌아간다. 그래서 테스트는 모델 발전에 따라 좋아질 것들보다 우리만의 약속·행동·도메인 specific한 것으로 구성해야 한다.
- ✅ 맞고, 글이 명시적으로 말한 것보다 한 걸음 더 나간 종합이다. 글은 "evals가 confidence를 준다"까지만 말하는데, 여기서 "그 테스트 스위트 자체가 모델 세대교체에도 살아남는 자산"이라는 걸 끌어냈다. 행동 평가가 재는 건 모델 성능이 아니라 "우리가 지키기로 한 행동"이라는 도메인 계약이라서, 모델을 바꿔도 그 계약은 그대로 유지돼야 한다는 논리가 맞물린다.

**⑤ 하네스도 모델 발전에 따라 가지치기될 수 있는가 (질문 → 확장)**
- 질문: 지금 하네스로 짜둔 것들에 테스트를 걸어두면, 나중에 모델이 바뀌었을 때 그 하네스가 불필요해졌는지도 테스트로 볼 수 있는가?
- 💡 한 단계 더: 원문에 직접 나온 내용은 아니지만 프레임워크에서 자연스럽게 따라 나온다. 단, **테스트가 통과한다는 것만으로는 판별 불가** — 하네스 요소(예: 시스템 프롬프트의 특정 지시문) 덕분에 통과하는 것과, 새 모델이 그 지시문 없이도 알아서 통과하는 것을 구분 못 하기 때문이다. 판별하려면 **같은 테스트를 유지한 채 그 하네스 요소만 제거(ablation)하고 통과율을 비교**해야 한다 — 통과율이 유지되면 그 요소는 이제 군더더기.

## ❓ 궁금증 → 해소

- **"행동 평가가 정확히 뭘 의미하나?"** → [행동 평가](../concepts/behavioral-evaluation.md). 원문 예시 3개(되묻기 / 완료 전 검증 / 정확한 링크 제공)가 공통적으로 "이 상황에서 이 행동을 했는가"라는 예·아니오 판정 단위라는 게 핵심.
- **"복잡한 작업은 어떻게 평가하나?"** → 엄격한 툴 시퀀스 강제 대신 [LLM-as-a-judge](../concepts/llm-as-a-judge.md) 방식의 느슨한 결과 기반 판정.

## 🔁 도메인 안 가리는 패턴 (전이 가능)
1. **큰 뭉치 점수보다 "이 상황 → 이 행동"으로 쪼개면 실패 원인이 바로 보인다.** 종합 점수는 무엇이 왜 틀렸는지 숨긴다.
2. **도구가 잘하는지보다, 지켜야 할 특정 행동을 체크리스트로 만들어두면 도구가 바뀌어도 체크리스트는 남는다.** (모델 세대교체·라이브러리 교체 어디든)
3. **안전장치가 여전히 필요한지는 "통과하는가"가 아니라 "빼도 통과율이 유지되는가"(ablation)로 판별한다.** 통과 자체는 안전장치가 일하는 중인지, 이미 필요 없어졌는지를 구분 못 한다.
4. **복잡한 자동화를 처음부터 설계하지 말고, 직접 써보며 감을 잡은 뒤에 체계화한다.** (dogfooding precedent)

## 🎯 오늘 챙길 한 줄
> 새 시스템·에이전트를 평가할 때 점수부터 보지 말고 "이 상황에서 이 행동을 했는가"로 쪼개라 — 그 체크리스트는 도구가 바뀌어도 남는 자산이고, 도구가 좋아지면 그걸 지키던 장치는 오히려 걷어낼 수 있는지 물어라.
