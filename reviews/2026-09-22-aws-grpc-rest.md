# AWS — gRPC와 REST 비교

## 🔑 한 줄 요약
> "가능한가"는 전송 계층(TCP)이 이미 답을 줬고, REST와 gRPC를 가르는 건 **그 위의 애플리케이션 계층이 그 능력을 어떻게 쓰기로 약속했는가**다 — REST는 리소스를 URI로, gRPC는 함수를 proto 계약으로 결합시킨다.

## 📌 무슨 글 (중립 요약)
- gRPC와 REST는 API를 설계하는 두 가지 다른 접근이며, 우열이 아니라 워크로드 특성에 따라 선택해야 한다.
- gRPC: 서비스(함수) 지향, Protocol Buffer + HTTP/2, 양방향 스트리밍 지원, proto로 코드 자동 생성, 긴밀한 결합.
- REST: 엔터티(리소스) 지향, HTTP 동사 + 보통 JSON, 요청-응답 1:1만 지원, 느슨한 결합.

## 🧠 내가 이해한 것 → 교정

**① 계층 구조: TCP → HTTP → REST/RPC**
- 내 생각: "tcp/udp와 같이 통신 계층에 프로토콜이 있고 보통 rest나 RPC는 tcp 계층으로 통신을 해. TCP는 3-way/4-way handshaking을 통해 서로 연결을 해서 신뢰가 되면 통신을 하는 걸 의미해."
- ✅ 맞음. handshake로 신뢰성 있는 연결을 여는 게 TCP의 핵심 → [TCP vs UDP](../concepts/tcp-vs-udp.md). 정확히는 REST·gRPC 둘 다 TCP "그 자체"가 아니라 TCP 위의 [HTTP](../concepts/http.md)를 통해 통신.

**② HTTP가 왜 나왔나**
- 내 생각: "데이터를 주고 받을 때 형식이 정해져 있지 않으면 매번 규약을 만들고 연결을 해야 하니 불필요한게 생겨서 http 개념이 나온거지."
- 🔧 교정: "연결을 매번 반복해야 하는 문제"가 아니었다. TCP는 그냥 바이트 스트림만 옮기고, 진짜 문제는 **"이 바이트들이 무슨 의미인지"에 대한 공통 약속이 없다**는 것. HTTP는 요청 줄/헤더/바디로 메시지 형식을 표준화해서 그 문제를 풀었다 → [HTTP](../concepts/http.md).

**③ REST와 RPC의 핵심 구도**
- 내 생각: "REST 방식은 주고 받을 데이터/문서를 URI 형태로 지정을 하고 http 메서드 방식을 동사형으로 사용해서 통신을 하는거지 ... RPC 방식은 클라이언트 쪽에서 서버쪽 method를 외부에서 동작하게 할 수 있는거지."
- ✅ 맞음. REST = 리소스(명사) + HTTP 메서드(동사), RPC = 원격 함수 호출 → [REST](../concepts/rest.md) · [RPC](../concepts/rpc.md).
- 💡 한 단계 더: 이 구도가 그대로 결합도로 이어진다 — REST는 URI/메서드만 알면 되니 느슨한 결합, gRPC는 proto로 함수 시그니처를 공유해야 하니 긴밀한 결합.

**④ gRPC 특성 정리 (서비스 지향 · Protobuf · 고성능 · 결합도-변경빈도)**
- 내 생각: "gRPC는 Protocol Buffer 형식을 기본 지원, json도 지원 ... 고성능 API를 생성할 수 있도록 설계 ... REST API는 커플링이 작기 때문에 변경이 잦은 소프트웨어 쪽에 적합, gRPC는 미리 선언적으로 만들어두고 자동 생기는 코드를 쓰기 때문에 변경이 덜 되는 곳에 적합."
- ✅ 맞음. 결합도-변경빈도를 직접 짝지은 추론이 원문의 "API 안정성 필요 — 시간이 지나도 변경 가능성이 낮은 환경"과 정확히 일치한다 (스스로 도달) → [gRPC](../concepts/grpc.md).

**⑤ HTTP 버전과 REST/gRPC**
- 내 생각: "일반적으로 웹/소프트웨어는 http 1.1 버전을 사용한다 ... 반대로 gRPC는 http 2로 사용된다."
- 🔧 교정: "REST=1.1, gRPC=2"로 딱 나뉘는 게 아니다. 오늘날 주요 브라우저는 HTTP/2를 기본 지원하고 REST API도 HTTP/2 위에서 흔히 돈다. 진짜 이유는 **gRPC가 HTTP/2의 멀티플렉싱·trailer 기능을 필수로 요구**해서 2가 아니면 동작 자체가 안 되는 것 — REST는 그 기능이 필요 없어서 1.1로도 충분할 뿐. (참고로 브라우저가 그 저수준 제어를 안 열어줘서 gRPC를 브라우저에서 직접 못 쓰고, `gRPC-Web`이라는 프록시가 따로 필요함) → [HTTP](../concepts/http.md).

**⑥ "proto 결합이 확장성을 낮추나?"**
- 내 질문: "gRPC는 ProtoBuf 형태로 서버쪽에서 데이터 형식을 지정해두고 쓰기에 클라이언트와 강하게 결합해서 확장성이 상대적으로 rest 방식보다 낮은건가? -> 서버쪽에 정의해두면 클라쪽에 proto 파일의 구조 정의에 맞게 코드를 생성해주기에 시간이 준다?"
- 🔧 답: "확장성"을 두 축으로 나눠야 한다 — **성능 확장성(scalability)**은 gRPC가 유리(바이너리+멀티플렉싱), **API 진화 용이성(evolvability)**은 REST가 유리(느슨한 결합). proto도 필드 번호 기반이라 새 필드 추가는 구버전을 안 깨뜨리게 설계돼 있어 "매번 깨진다"는 아니고 "조율 비용이 더 크다" 정도가 정확 → [Protocol Buffers](../concepts/protocol-buffers.md).
- 코드 자동생성으로 개발 시간이 준다는 부분은 ✅ 맞음.

**⑦ "TCP도 양방향인데 gRPC만 양방향이라는 게 이상하지 않나?"**
- 내 질문: "gRPC는 양방향 통신을 지원하고 REST는 안한다고 하는데 TCP에서도 양방향 스트리밍이 가능하다고 얘기를 들은거 같은데 아닌지?"
- 💡 정확한 직관. TCP는 원래 full-duplex(양방향)다 — gRPC가 새로 만든 능력이 아니다. 차이는 **"가능한가"가 아니라 "그 위의 애플리케이션 계층이 그 능력을 어떻게 쓰기로 약속했나"**다. REST는 요청-응답을 1:1로 고정해버렸고, gRPC(HTTP/2)는 하나의 연결 위에 여러 독립 스트림을 정의해서 그 능력을 명시적으로 노출한다 → [TCP vs UDP](../concepts/tcp-vs-udp.md).

## ⚖️ 비교표

| | REST | gRPC |
|---|---|---|
| 설계 관점 | 엔터티(리소스) 지향 | 서비스(함수) 지향 |
| 데이터 포맷 | 보통 JSON (텍스트) | Protocol Buffers (바이너리), JSON도 가능 |
| 통신 모델 | 요청-응답 1:1만 | 단방향/서버·클라이언트/양방향 스트리밍 |
| 결합도 | 느슨함 | 긴밀함 (proto 공유 필요) |
| 코드 생성 | 없음 (서드파티 필요) | proto → 클라/서버 코드 자동 생성 |
| 적합한 곳 | 공개 API, 변경 잦은 서비스, 브라우저 클라이언트 | 내부 마이크로서비스, 고성능·대용량·실시간 스트리밍 |

## 🔁 도메인 안 가리는 패턴
1. **비교가 헷갈리면 계층부터 맞춰라.** 서로 다른 층(전송/프로토콜/설계스타일/구현체)에 있는 개념을 같은 선상에 놓고 비교하면 혼란이 생긴다.
2. **"가능한가"와 "그렇게 쓰기로 약속했는가"는 다른 질문이다.** 하부 계층의 잠재력(TCP의 양방향)과 상위 계층의 의미론적 계약(REST의 1:1, gRPC의 스트림)을 구분해서 봐야 한다.
3. **모호한 단어는 축을 나눠라.** "확장성"처럼 뭉뚱그려 쓰이는 단어는 트레이드오프를 말할 때 성능/진화 용이성 같은 서로 다른 축으로 쪼개서 각각 판정한다.
4. **결합도와 변경 빈도는 짝이다.** 느슨한 결합(REST)은 변경이 잦은 곳에, 긴밀한 결합+코드 생성(gRPC)은 API가 안정적인 곳에 적합.

## 🎯 오늘 챙길 한 줄
> 두 기술을 비교할 땐 먼저 계층을 맞추고, "무엇이 가능한가"와 "무엇을 하기로 약속했는가"를 나눠서 봐라.
