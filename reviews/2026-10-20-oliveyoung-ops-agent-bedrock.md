# 올리브영 — AI 기반 운영 이슈 분석과 일일 점검 자동화

## 🔑 한 줄 요약
> 병목은 분석 자체가 아니라 "어디서 무엇을 어떻게 이어 붙이면 피해가 나오는지"를 아는 사람이 개발자뿐이라는 것 — 정의할 수 있는 판정은 코드, 해석은 LLM, 보상 같은 책임은 운영자에게 나눠 1~2일을 약 5분으로 줄였다.

## 📌 무슨 글
- 미국 진출로 프로모션 시간대가 한국 근무 시간과 안 겹쳐, 장애 때마다 한국 개발자의 로그·주문·쿠폰 분석을 기다리던 병목을 에이전트 두 개로 푼 사례다.
- 인시던트 분석 에이전트(장애 후, 고객 피해 산정과 보상안 후보)와 데일리 헬스 체크 에이전트(정시 자동 실행, 5개 수집기 → 8개 영역 리포트). 스택은 Bedrock(Claude) + Strands + AgentCore Runtime + Datadog MCP + OpenSearch.
- 수치(5분, 32만 건 오류를 1분 내 분석)는 글의 주장이다. 에이전트 간 공유 로직, 인시던트 유형 분류의 주체, 기존 AWS DevOps 에이전트 대신 직접 만든 이유는 글에서 확인하지 못했다.

## 🧠 내가 이해한 것 → 교정

**① ECS는 쿠버네티스 역할이고, Fargate는 "서버 컨테이너" 정도인가**
- 내 생각: ECS가 컨테이너를 런타임에 어떻게 관리할지 돕는 도구이고, Fargate는 서버 컨테이너 정도.
- ✅ ECS ≈ 오케스트레이터 맞음. → [ECS와 Fargate](../concepts/ecs-fargate.md)
- 🔧 교정: Fargate는 컨테이너가 아니라 **컨테이너가 올라탈 서버를 AWS가 대신 마련해주는 실행 방식**이다. ECS = 무엇을 몇 개 돌릴지, Fargate = 어디서 돌릴지.

**② 글은 개발자의 분석·전달이 병목인 상황을 코드와 에이전트로 푼 것**
- 내 생각: 비즈니스 로직이 개발자의 데이터 분석/결과 전달에 걸려 병목이 됐고, 그걸 코드와 에이전트로 해결했다.
- ✅ 맞음. 문제 정의와 일치.
- 🔧 교정: 병목의 정체는 "분석이라는 작업"보다 **절차가 개발자 머릿속에만 있었다**는 것이다(데이터 4~5곳 분산, 시간대 불일치, 오류 건수로는 피해를 못 구함). 해법도 분석을 빠르게가 아니라 **그 절차를 시스템으로 옮기기**.

**③ 수집할 데이터, 평가 방식, 다음 액션만 정의되면 에이전트가 수집·판단까지 가능하다**
- 🔧 교정: 절반만 맞다. 글에서 **판정은 코드**(피해 금액, 7일 기준선·임계치)이고 LLM은 해석·근거 정리만 하며 계산값을 못 바꾼다. **액션은 제안까지가 에이전트**, 보상 승인과 Monitor 반영은 운영자다.
- 🔧 교정: "충분"이 아니라 **필요조건**. 같은 조건인데 설명이 달라지고 응답이 느렸던 초기 구현, 소량 트래픽·미완료 집계의 오탐이 따로 남았다.
- 💡 병목이 사라진 게 아니라 **옮겨갔다** — 장애마다 하던 분석에서 처음에 규칙을 정의하는 일로.

**④ 에이전트를 두 개로 나누고, 기반만 있으면 장애 시와 주기 점검 둘 다 가능하다**
- ✅ 구조 관찰 맞음: 반응형(장애 후)과 주기형(정시 + 수동 재실행).
- 🔧 교정: 재사용되는 건 **판단 로직이 아니라 판단을 돌리는 틀**(Strands·AgentCore·Datadog MCP·코드/LLM 분업)이다. 판단 규칙과 입출력은 별개(피해 산정 vs 기준선 비교). 두 에이전트가 로직을 공유하는지는 글에서 확인 못 함.
- 💡 왜 둘인지는 추정: 무너지는 조건이 다르다(인시던트는 판정 오류, 헬스 체크는 오탐 누적).

**⑤ 각 레이어에서 이미 잘 만들어진 도구를 활용한다**
- ✅ 맞음. 모델·에이전트 루프·호스팅·연동·인프라 전부 빌려 썼다. → [Bedrock · Strands · AgentCore](../concepts/bedrock-agentcore-strands.md)
- 🔧 교정: 직접 만든 곳이 글의 핵심이다 — 고객 영향 금액 계산, 판정 기준(임계치·최소 호출 수·미완료 집계 제외), 유형별 조회 규칙. 빌린 건 **어떻게 돌리느냐**, 만든 건 **무엇이 맞는 답이냐**.

## 📚 이 글로 정리한 개념
- [VPC와 public/private subnet](../concepts/vpc-subnets.md) — 다이어그램에서 ALB는 public, Admin Backend는 private에 둔 이유(최소 노출).
- [ECS와 Fargate](../concepts/ecs-fargate.md) — Admin Backend를 서버 관리 없이 돌리는 방식, K8s와의 대응.
- [Bedrock · Strands · AgentCore](../concepts/bedrock-agentcore-strands.md) — 에이전트 스택 세 층. 공식 문서로 교차 확인한 내용.
- [AI-DLC](../concepts/ai-dlc.md) — 이 시스템을 만든 개발 방법론(글의 참고자료에 도입 사례 글이 별도로 있다).
- [MCP](../concepts/mcp.md) — Datadog 로그·APM·Trace를 에이전트가 조회하는 통로.

## 🔁 도메인 안 가리는 패턴

1. **정의할 수 있는 판단은 코드로, 정의할 수 없는 해석은 LLM으로, 책임이 걸린 결정은 사람에게.**
   - 계산값을 LLM이 못 바꾸게 막고, 에이전트는 후보를 **제안**하고 사람이 **반영**한다.
   - ([DEVOCEAN 노트](2026-08-25-devocean-dynamic-workflow.md)의 "결정적 제어와 확률적 실행을 분리"와 같은 모양. [NHN 노트](2026-10-06-nhn-harness-silver-bullet.md)의 "제안은 AI, 반영은 사람", [SAGE 노트](2026-08-24-ly-sage-security-agent.md)의 "판단 준비/판단" 절단면과도 같은 모양)
2. **자동화는 병목을 없애지 않고 옮긴다 — 반복 분석에서 최초 정의로.** 정의를 한 번 잘 해두면 반복 비용이 0에 가까워지고, 잘못 정의하면 그 오류가 매번 자동으로 반복된다.
   - 가장 어려운 건 지표의 정의다("오류 건수 ≠ 영향 고객 수"). 틀리면 수집·판정이 자동이어도 결론이 틀린다.
   - 판정 코드엔 "판정하지 않을 조건"도 정의해야 한다(소량 트래픽, 미완료 집계, 수집기 하나가 죽어도 나머지 유지).
   - ([미리디 노트](2026-08-18-miridih-qa-automation.md)의 "반복과 전달을 걷어내 사람의 판단 시간을 돌려줘라"와 같은 모양)
3. **같은 기반 위에 트리거만 다른 두 얼굴(반응형/주기형)을 올리되, 재사용되는 건 틀이지 규칙이 아니다.** 나눌지는 "무너지는 조건이 같은가"로 가른다.
4. **범용 레이어는 빌리고, 도메인 판단 기준만 직접 쓴다.** 직접 만들 부분을 도메인 지식이 있는 곳으로 좁힌다.

## 🎯 오늘 챙길 한 줄
