# SSG — 기획자의 AI 테스트 자동화 도전기 (1·2편)

## 🔑 한 줄 요약
> 시간이 지나야 드러나는 정책(월말 보정, 캐시백 횟수)은 "가입 → 결제 ×N" 시나리오를 날짜 입력으로 압축해 시험하고, 자동화를 늘리면 수동 비용은 유지보수 비용으로 옮겨가니 공통 모듈·DTO·컨텍스트로 구조를 먼저 잡는다 — 다만 기대값을 구현과 같은 로직으로 다시 계산하면 같은 오해가 두 번 통과한다.

## 📌 무슨 글
- 1편(2026-09-01): 연 멤버십에서 월 멤버십(쓱7클럽)으로 개편되며 가입일자별 이용기간·결제일(1/29~31 가입자는 2/28 결제 후 3월부터 원래 일자 복귀)을 수동으로 반복 검증했다. 기획자가 ChatGPT·Gemini로 Python(`pandas`·`httpx`·`pytest`)을 짜 CSV 기대값 ↔ 가입 API 응답을 `assert`로 비교. 1 Cycle 3분 → 25초(약 86% 단축).
- 2편(2026-10-26): 케이스마다 AI로 코드를 따로 만들다 중복·분산 수정이 생겼다. 파일/API/DB/로그/설정 공통 모듈로 분리, API 응답+DB 조회를 DTO 하나로 통합, 기능 모듈을 조합하는 시나리오(`ScenarioContext`)로 캐시백 정책(유료 결제 후 해지 제외, 최초 유료결제월별 3/2/0회)을 `for`로 일괄 검증.
- 글에 없는 것: 개발 쪽 테스트 현황, 2편의 정량 결과, 캐시백 "27년 1월~"는 TBD.

## 🧠 내가 이해한 것 → 교정

**① 두 달만 쓰면 28·29·30일 가입자가 손해 아닌가?**
- 내 질문: 월 멤버십 개편에서 1월 28/29/30일 가입자에 따라 두 달만 쓰는 사람은 손해 보는 경우가 있지 않나.
- 🔧 교정: **2개월 총 이용일수는 같다.** 2월에 28일로 당겨도 3월부터 원래 일자로 복귀하므로 1/28·29·31 모두 "1월 x일 ~ 3월 x일 전날" = 59일. 복귀 없이 28일에 고정되는(앵커가 당겨지는) 구현이어야 손해가 쌓이고, 글이 "3월부터 복귀"를 따로 검증한 이유가 그 버그다 → [월 반복 결제의 앵커 날짜](../concepts/billing-anchor-date.md).
- 남는 진실: **1개월만 쓰고 해지**하면 1/31 가입자 28일, 1/28 가입자 31일로 실제 차이가 난다(달 길이가 다른 월 구독 일반의 성질).
- 한계: 글에 가격과 기간 끝 규칙이 없다. "결제일 전날까지 이용"은 내가 둔 가정.

**② "구조 분리·공통 로직 추출은 개발자라면 당연한 내용"**
- 내 생각: 테스트를 하려면 역할/도메인별 분리, 공통 로직 추출은 엔지니어에겐 당연하다.
- ✅ 맞음. 2편의 문제(복붙 → 수정 분산)와 해법은 흔한 성장 경로다.
- 💡 한 단계 더: 이 글에서 새로운 건 구조가 아니라 **정책 검증용 시나리오**다. "가입 → 정기결제 ×3" 같은 행동 순서를 모듈 조합으로 쓰고, `datetime.now() + relativedelta(months=i-7)`로 **결제 예정일을 입력으로 밀어** 시간 경과를 흉내 낸다(코드에서 읽은 것; 서버 시계를 돌리는 방식이 아님).

**③ 기획자가 개발 역할까지 맡은 건가? 개발자가 테스트를 안 짠 건가?**
- 내 생각: 이미 개발된 상태에서 기획자가 테스트하는 게 의아하다. 개발자가 테스트 코드 없이 작업했나 의심.
- 🔧 교정: **글에 근거가 없는 추측**이다. 지지하는 문장도 반박하는 문장도 없다. 열린 질문으로는 좋지만 결론으로는 못 쓴다.
  - 이 테스트는 실제 API 호출 + DB 데이터 생성/삭제 + 여러 호출 연결이라 **인수·통합 층**이다. 개발자의 단위 테스트(날짜 계산 함수)가 있어도 "정책 문서대로 동작하나"를 정책 소유자가 확인하는 건 다른 층의 일이다 → [완료 기준](../concepts/acceptance-criteria.md)과 같은 계열.
  - 기획자가 만든 이유는 둘 다 가능 — 개발 쪽 테스트 공백 / 정책 소유자의 인수 검증. 글만으로는 구분 불가.

**④ (대화 중 짚은 점) 기대값을 구현과 같은 로직으로 다시 계산한다**
- 2편의 `check_exp_ssgmy_rsv_tgt`는 정책(해지 제외, 횟수 계산)을 **테스트 코드 안에서 다시 구현**한다. 정책이 바뀌면 서비스와 테스트 두 곳을 고쳐야 하고, 둘이 같은 오해를 하면 통과한다. 1편의 CSV(사람이 계산한 기대값)가 오히려 더 독립적이다 → [테스트 오라클](../concepts/test-oracle.md).
- 사용자가 스스로 도달한 건 아니고 💡로 던진 것이다. 이후에 사용자가 이어서 팠는지는 대화에 없다.

## 🔁 도메인 안 가리는 패턴

1. **시간이 지나야 드러나는 규칙은 시간을 입력으로 만들어 압축해서 시험한다.** 월말 보정, 갱신 횟수, 만료 같은 규칙을 실제 달력으로 기다릴 수 없으니, "날짜를 주입할 수 있는 지점"이 시험성의 핵심이다. 그 지점이 없으면 시나리오 자동화도 못 한다.
2. **기대값의 근거(오라클)가 구현과 같은 정보원이면 같은 오해를 두 번 통과시킨다.** 사람이 계산한 표, 불변식(가입일이 달라도 2개월 총일수 같다) 같은 성질이 다른 근거가 있어야 두 번째 겹이다. ([원티드랩 노트](2026-08-06-wantedlab-agent-loop.md)의 "두 번째 안전장치는 첫 번째와 성질이 달라야 한다", [한컴 노트](2026-08-27-hancom-unity-react-migration.md)의 "기준을 명세로 외재화"와 같은 모양. [LY E2E 노트](2026-10-16-ly-ai-e2e-test-pipeline.md)의 "합격 기준을 고정하라"도 이어진다.)
3. **자동화는 수동 비용을 없애지 않고 유지보수 비용으로 옮기고, AI는 생성이 싸서 그 부채를 더 빨리 쌓는다.** 케이스 하나당 코드를 뽑으면 중복이 늘어 "공통 로직 변경 = 여러 파일 수정"이 된다. 3분→25초는 실행 시간이지, 2편의 구조 개선 비용은 그 숫자에 안 잡힌다. ([원티드랩 노트](2026-08-06-wantedlab-agent-loop.md)의 "줄어든 건가, 옮겨간 건가?"와 같은 모양)
4. **정책을 검증할 사람이 그 정책을 가장 정확히 아는 사람일 수 있다.** 단 그 사람이 만든 검증이 구현과 독립인지는 별개로 확인해야 한다(2번).

## 📚 이 글로 정리한 개념

- [테스트 오라클](../concepts/test-oracle.md) — 기대값을 정하는 근거. 구현을 다시 계산하면 검증이 아니다.

## 🎯 오늘 챙길 한 줄
