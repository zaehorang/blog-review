# 이랜서 — NGINX란? 왜 대부분의 서비스는 NGINX를 앞단에 둘까?

## 🔑 한 줄 요약
> 앞단 게이트웨이의 정체는 "트래픽 분산"이 아니라 **여러 서비스를 하나의 주소로 보이게 하는 진입점**이고, 필요 여부는 Nginx 유행이 아니라 **서비스가 몇 개의 별개 배포 단위로 쪼개졌는가**가 정한다.

## 📌 무슨 글 (중립 요약)
- Nginx는 웹 서버로 시작했지만 실운영에선 앱 서버 앞단의 리버스 프록시로 쓰인다. 정적은 직접, 동적만 내부로 넘기고 필요하면 분산.
- 이벤트 기반 비동기(워커 하나가 여러 연결)라 프로세스/스레드 증설 방식보다 메모리 부담이 적다는 주장. Apache와 비교, 기본 사용법, 502/504·리다이렉트 루프 점검 순서.
- 글에 없는 것: 캐시 설정 본문(FAQ 제목만), 측정 수치("수만 개"만), Nginx 자체가 단일 장애점이 되는 문제.

---

## 🧠 내가 이해한 것 → 교정

**① 정의와 구조**
- 내 생각: 정적은 직접(nginx도 웹서버니까!), 동적은 여러 내부 서버로 분산하는 리버스 프록시. 클라우드/컨테이너가 생겼다 사라지니 앞단 게이트웨이로 자리 잡음.
- ✅ 맞음. 🔧 다만 "여러 서버로 분산 = 리버스 프록시"는 절반 — **정의는 서버 앞에서 대신 받아 전달**이고, 서버 1대여도 리버스 프록시. 분산은 그 위의 기능 하나 → [리버스 프록시](../concepts/reverse-proxy.md).

**② "이벤트 기반으로 여러 서버로 분산 처리해준다?"**
- 🔧 교정: **서로 다른 두 가지를 묶었다.** 이벤트 기반은 한 프로세스가 연결을 다루는 방식(동시성 모델), 분산은 요청을 어느 서버로 보낼지(라우팅). 독립이다 → [이벤트 기반 동시성](../concepts/event-driven-concurrency.md).

**③ "웹서버는 UI쪽, 애플리케이션 서버는 도메인 로직?"**
- ✅ 앱 서버 쪽은 맞다(코드를 실행). 🔧 웹 서버는 UI를 만드는 게 아니라 **이미 만들어진 파일을 내주거나 뒤로 전달만 하는 문**. "코드를 실행하나, 내주거나 전달만 하나"로 가르면 된다.

**④ "이벤트 수가 많으면 메모리도 똑같이 필요한 거 아닌가?" (제일 값진 질문)**
- 🔧 교정: 줄어드는 건 일의 양(CPU)이 아니라 **기다리는 연결의 비용**. 연결 대부분은 대기 중인데, 스레드 모델은 대기 중에도 스택·전환 비용을 내고 이벤트 모델은 작은 상태 구조체일 뿐. **연결은 많고 대부분 대기인 워크로드에서 이득이 크고, CPU 바운드면 작다**(글엔 이 조건이 없다).
- 💡 응용: Nginx가 느린 클라이언트를 대신 받아주면 앱 서버 워커가 그 대기에 안 묶인다 — "앱 서버가 비즈니스 로직에 집중"의 실제 의미.

**⑤ Apache vs Nginx / reload**
- 내 생각: Apache는 MPM으로 모델 선택, Nginx는 이벤트 기반 고정. `.htaccess`는 사용자별 위임에 유용. reload는 무중단.
- ✅ 맞음. 💡 `.htaccess`가 느린 이유는 요청마다 디렉터리를 거슬러 올라가며 파일을 확인하기 때문("편한 위임 ↔ 요청마다 드는 비용"). reload는 새 워커를 띄우고 옛 워커가 끝나길 기다리며, 문법이 틀리면 reload가 실패하고 옛 설정이 유지된다 → 그래서 `nginx -t`. (글엔 `Nginx -s reload` 대문자 오타.)

**⑥ 502/504**
- 내 생각: 502는 연결 이슈, 504는 설정 시간 안에 응답 못 함. 점검: 앱 서버 → `proxy_pass` 주소·포트 → 방화벽 → 타임아웃.
- ✅ 504, 점검 순서는 정확. 🔧 502를 "연결 이슈"로만 보면 절반 — **연결은 됐는데 업스트림이 비정상/끊긴 응답**을 준 경우도 502.
- 💡 `error.log` 한 줄이 후보를 가른다(`connection refused` vs `upstream timed out`) — 4단계를 밟기 전에 로그부터.

## ❓ 궁금증 → 해소 (글 맥락)

- **프록시가 뭔가, 왜 "리버스"?** 내 추측: 외부 앱 서버로 요청 보내는 것. → 🔧 뒤쪽은 외부가 아니라 내부, 핵심은 **누구의 대리인이냐**(포워드=클라이언트, 리버스=서버). "업스트림으로 보낸다"는 맞고, 보내는 건 이벤트가 아니라 요청.
- **리다이렉트 루프?** 앞단이 HTTPS를 풀어(TLS 종료) 앱에 http로 넘기면, 앱은 원래 https였는지 몰라 또 https로 리다이렉트 → 무한 반복. 해결은 `X-Forwarded-Proto`. → [HTTPS와 TLS 종료](../concepts/tls-termination.md) · [HTTP 리다이렉트와 루프](../concepts/http-redirect.md). (HTTPS를 이해하고 나서야 풀린다는 내 직감이 맞았다.)
- **캐시?** 내 이해(자주 요청되는 응답을 앞에서 대신 줘 서버 부담 줄임) ✅. 💡 **"누구에게 줘도 같은 응답"에만 안전**하다 — 사용자별 응답을 캐시하면 노출 사고. 글은 캐시 설정을 본문에서 다루지 않는다.

## 💬 현장 질문: "Nginx(게이트웨이)가 꼭 필요한가?" (멘토에게 직접 질문)

내가 멘토에게 던진 질문과 답을 따라간 기록. 내 이해가 단계마다 교정됐다.

**⑦ "결국 트래픽 분산 정도?"** → 🔧 **내부 서비스로 전해주는 gateway**. `/` → web, `/auth` → keycloak, `/api` → be로 라우팅해 **클라이언트는 하나의 주소**만 안다. 분산이 아니라 진입점 통합.
**⑧ "클라는 여러 서버를 알 필요 없이 하나의 주소, 내부에서 나눠 보내는 역할?"** → ✅ (멘토 확인). 다듬을 점: 게이트웨이가 auth/api가 되는 게 아니라 뒤의 별개 서비스로 **전달하는 쪽**.
**⑨ "엔드포인트를 안 나누고 서버 하나면 게이트웨이 굳이 없어도?"** → ✅ FastAPI+Jinja2, 정적 HTML/CSS/JS도 하나로 가능. 💡 "필요 없을 수도"이지 "필요 없다"는 아님(TLS·캐시 등 다른 이유).
**⑩ "auth와 be가 서로 다른 서버/프로세스라서 게이트웨이가 필요한 건가?"** → ✅ (스스로 도달). 게이트웨이의 필요는 **별개 배포 단위의 개수**에서 나온다.
**⑪ "프로젝트 하나에 be·auth 두 엔드포인트를 한 번에 배포하는 느낌이었다"** → 🔧 **엔드포인트(URL 경로)와 서비스(배포 단위)는 다른 층위.** `/auth`·`/api`는 경로일 뿐이고 뒤에는 **각각 따로 배포되는 별개 서비스**(k8s라면 한 네임스페이스 안 별개 서비스). 경로가 여럿이어도 서비스가 하나면 게이트웨이는 불필요. → [K8s Ingress](../concepts/kubernetes-ingress.md)
**⑫ "인증도 be에서 하면 되지 않나?"** (멘토가 선제 답변) → 신뢰할 수 있는 OIDC를 쓰기로 했고 **교체 가능**(tnet)하기를 기대하므로 별도 서비스. 💡 바뀔 수 있는 것·검증된 외부 표준은 비즈니스 로직에서 분리한다.
**⑬ "서비스는 따로 개발하고 완료한 뒤 k8s에 연결? config도 직접?"** → ✅ docker compose의 yml과 같은 **선언형 설정**. BE는 비즈니스 로직, config는 devops, 운영 기준은 SRE — 단 **칼같이 안 나뉘고** BE가 하는 일도 많다 → [선언형 설정](../concepts/kubernetes-workload-basics.md#선언형-설정--compose-yml-vs-k8s-yaml).
**⑭ "k8s에서는 ingress가 L7 로드밸런싱"** → ✅. L4는 IP·포트만, L7은 HTTP 내용(경로·호스트)까지 보고 라우팅. Ingress는 규칙, 실행은 Controller(Traefik 등 — "확정 아님"이 가능한 이유) → [네트워크 계층](../concepts/network-layers.md)의 L4/L7 절.
**⑮ CORS?** 출처(프로토콜+호스트+포트)가 다르면 브라우저가 응답을 JS에 안 주는 규칙. 게이트웨이로 한 주소에 묶으면 **같은 출처**라 규칙이 필요 없다 → [CORS](../concepts/cors.md).

## ⚖️ 앞단을 둘 때 vs 안 둘 때

| | 앞단 없음 | 앞단(리버스 프록시/게이트웨이) |
|---|---|---|
| 적합 | 서비스 1개, 서버 1대 (앱이 직접 응답) | 서비스가 **둘 이상의 별개 배포 단위**, 다중 서버 |
| 클라이언트가 아는 것 | 서버 주소 | **주소 하나** |
| CORS | 출처가 다르면 필요 | 한 출처로 묶으면 불필요 |
| TLS·캐시·느린 클라 | 앱이 부담 | 앞단이 흡수 |
| 대가 | 없음(단순) | 운영 대상 +1, 설정 실수(502/504·리다이렉트 루프) |

## 🔁 도메인 안 가리는 패턴 (전이 가능)
1. **필요 여부는 도구의 유행이 아니라 "구조가 무엇으로 쪼개졌는가"가 정한다.** 쪼개진 배포 단위가 둘 이상이면 이들을 하나로 묶는 진입점이 필요하고, 하나면 필요 없다. (필수인 건 구현체가 아니라 **역할** — Nginx → Traefik로 갈아 끼워도 규칙은 그대로.)
2. **"경로(주소 체계)"와 "서비스(배포 단위)"를 구분해라.** URL이 여러 갈래라고 시스템이 여러 개인 건 아니다. 층위가 다른 것을 한 줄에 놓으면 헷갈린다. ([AWS gRPC 노트](2026-09-22-aws-grpc-rest.md)의 "비교가 헷갈리면 계층부터 맞춰라"와 같은 모양)
3. **줄어드는 게 일이 아니라 "대기 비용"인지 물어라.** 이벤트 기반처럼 효율을 주장하는 구조는 *어느 워크로드에서* 이득이 나는지 조건이 따라붙는다(대기가 많을 때). 조건 없는 "빠르다/적게 쓴다"는 절반만 말한 것.
4. **규칙(선언)과 실행(구현)을 분리하면 구현체를 교체할 수 있다.** Ingress(규칙) vs Controller(실행). ([K8s 노트](2026-09-28-devocean-k8s-inference.md)의 "뭉뚱그려 보이는 추상화도 뜯으면 정책/데이터/실행이 분리돼 있다"와 같은 모양)
5. **계층을 하나 얹으면 앞 계층의 정보가 사라진다.** TLS를 앞단에서 풀면 뒤의 앱은 "원래 https였다"를 모른다 → 사라진 정보를 헤더로 다시 실어 보내지 않으면 루프가 난다. 프록시·게이트웨이·캐시 등 중간 계층이 낀 곳에서 공통.
6. **변하는 것·검증된 외부 표준은 비즈니스 로직에서 분리해라.** 인증을 OIDC 별도 서비스로 둔 이유는 "교체 가능성". 분리 기준은 코드 크기가 아니라 **교체/변경 주기가 다른가**.

## 🎯 오늘 챙길 한 줄
> 앞단 계층이 필요한지 판단할 땐 "트래픽이 많은가"가 아니라 **"클라이언트가 알아야 할 서버가 몇 개로 쪼개졌는가"**를 물어라. 하나라면 없어도 되고, 둘 이상이면 하나의 주소로 묶는 역할이 필요하다 — 그 역할을 Nginx가 하든 Traefik이 하든.
